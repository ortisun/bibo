# Security review of repository registration, the project-map gate and the issue status writer

- Reviewer: an independent security reviewer (Claude Sonnet 5.5), working alone from the repository. I wrote none of the code under review and changed none of it. My only addition is this document. I wrote no test target.
- Date: 2026-11-02. Reviewed commit: `7e58ec9` (`feat/slice-0-foundation`). Part A is the merge `4e34c4f` (`git diff cc3fa7e...worktree-agent-aa1574f8f86c7a770`). Part B is the merge `7e58ec9` (`git diff cc3fa7e...worktree-agent-a1e7feca75f0d4692`).
- Question: (A) can registration, the attestation of the project map and the enabling of a repository be used to bind another party's webhooks, to enable a repository nobody looked at, or to write on the database what a person did not do; (B) can the status writer write the wrong label, write on the wrong issue, widen a credential, carry untrusted text, or hurt a job or the App's budget.
- Environment: reading only. `git show`, `git diff`, `git grep`, file reads. I did not run `cargo`, the test suites, PostgreSQL or Docker (a long test run was using the machine, and I was told not to). **Every statement below is from reading the code, not from running it.** Where I rely on GitHub behaviour that nobody in this repository has observed, I say "unverified".
- Evidence: none by test. Each finding names the file and line, the scenario, why the existing tests do not catch it, and a fix.

## 1. Verdicts

| Area | Verdict |
|---|---|
| A. Registration, project-map attestation, enable and disable (migration, store, API, CLI) | **PASS WITH CONDITIONS** |
| B. Issue status write-back (ports v1.2: policy type, adapter, token, worker step) | **PASS WITH CONDITIONS** |

Overall: **PASS WITH CONDITIONS**, for use by the builders and one tenant. **I found no BLOCKER.** I looked hardest for one in three places: a registration that gives the factory a credential for somebody else's repository, a status label that is the trigger label or a `design:` label, and a status token wider than `issues: write` for one repository. All three held, and for reasons that are partly not the ones the documents give. The credential for a repository comes from a static configuration list (`crates/composition/src/external.rs:268-290`) and not from the row that registration writes. The trigger label can only start a job when its sender is a registered, allowlisted person (`apps/api/src/webhook.rs:199-207`), and intake re-reads GitHub (AUT-11). The label type is a second barrier on top of those.

**Why not PASS.** Two things.

1. **REG-1.** A repository that is already enabled stays enabled when a different commit of the project map is attested. The person who enabled it (an approver) never sees the new commit, and the person who replaced it needs only the weaker `operator` designation. The commit is read by nothing else in the engine, so the gate is "someone attested something once".
2. **REG-2.** The API's database login can now register, attest and enable with plain column grants and an unsigned audit row. Decisions of people do not work this way: since AUT-12 they are signed requests that the worker applies. The migration's own justification ("the same limit holds for the decision requests", `up.sql:32`) is out of date, so the new path is **weaker than the one it was said to match**.

**Conditions.** Close REG-1 before the first real repository is enabled. Close or consciously accept REG-2, with an owner and a date, before the API database credential leaves the builders' hands. REG-3 (registration trusts what the operator types) is harmless with one tenant and is a **hard precondition for a second tenant**: it would be a BLOCKER at that point. Part B has no MAJOR finding. Its ten smaller findings concern the accuracy of the documents, back-off, races and the worker start. None stops a first trial, but STS-7 (the worker start) and STS-2 (the retry schedule) should be fixed before the first run against a real GitHub; the rest can follow.

**What the verdict does not cover.** Everything that needs the real GitHub (section 6), a running worker with a database and an App, and the Python tool and the GitHub Action that revert labels.

## 2. Severity scale

BLOCKER: do not use against a real GitHub, or by anyone but the builders, until closed. MAJOR: a control the documents promise is weaker than promised, or a party can reach further than its designation, and the fix is cheap before wider use. MINOR: defence in depth, a wrong reason, an inaccurate claim, observability. NOTE: worth knowing, no action needed now. There is no BLOCKER.

### REG-1. Attesting another commit does not switch an enabled repository off (MAJOR)

- **Evidence.** The attest statement sets `project_map_commit`, `project_map_attested_by_principal_id` and `version` and nothing else (`crates/storage/src/pg/jobs.rs:982-1022`). The trigger only checks the attestor and stamps the time (`migrations/2026-11-02-002400_repository_project_map/up.sql:79-100`). The CHECK is `NOT enabled OR project_map_commit IS NOT NULL` (`up.sql:70-71`), which any commit satisfies. The handler never reads `row.value.enabled` (`apps/api/src/repositories.rs:416-464`). The roles differ: `confirm_project_map` needs `operator`, `enable_repository` needs `approver` (`policies/approval.yaml:242-243`).
- **Scenario.** An approver reads the map at commit C1 and enables the repository. The audit row says "attested at commit C1". Later an operator posts `project-map` with C2, or with the tip of the branch "to bring it up to date". The repository stays enabled, webhooks keep binding, jobs keep starting. Nobody with the `approver` designation looked at C2. A second route to the same end: disable, then enable again. The second enable needs no new attestation and passes (the test asserts a 200, `apps/api/tests/repositories.rs:296`), so an attestation from months ago enables a repository today.
- **Why the tests miss it.** No test re-attests while the repository is enabled. `docs/database/tests/repository_map.sql:150-165` switches the repository off first, then changes the commit. The API test attests a new commit on a repository that was never enabled (`apps/api/tests/repositories.rs:760-800`). The contract suite attests before enabling (`crates/testkit/src/contracts/store.rs:3321-3493`; I did not read each case).
- **Fix.** Make the loss of `enabled` part of the same change. In the attest statement, `SET enabled = CASE WHEN project_map_commit IS DISTINCT FROM $4 THEN false ELSE enabled END`, and write a `repository.disabled` audit record in the same transaction with the reason "map attested again; enable it again". Better, put it in the table so a raw writer cannot skip it: a `BEFORE UPDATE` rule in `repositories_project_map_guard` that sets `NEW.enabled := false` when the commit or the attestor changes while `OLD.enabled`. Also require a fresh attestation after a disable (clear the three columns on disable, or compare `enabled_commit` with `project_map_commit` in a CHECK). Add the missing tests: re-attest while enabled, and enable-after-disable.

### REG-2. The API login's new write grants are weaker than the signed-request pattern (MAJOR)

- **Evidence.** The login gets `INSERT` on six columns and `UPDATE` on four (`up.sql:109-112`), and four more audit actions (`up.sql:115-132`). The audit row is built without any keyed word (`apps/api/src/repositories.rs:280-307`, `310-325`). A decision of a person is different: `crates/composition/src/decision_signing.rs:14` describes the `mac=` word, the worker verifies it before it reads anything else, and the threat model says "the worker applies only records the API signed" (`docs/security/threat-model.md`, T-38, mitigations). The migration states the residual risk, then says "the same limit holds for the decision requests of people until the deployment narrows the login further" with a pointer to AUT-12 (`up.sql:29-33`). AUT-12 is fixed (`docs/reviews/authority-and-evidence-security-review.md`, section 10, row AUT-12). The sentence is out of date and understates the change.
- **What compromise allows now that it did not before.** Before this migration the API login could append jobs, original requests, webhook deliveries and 15 kinds of audit row, and could not change any row. A holder of its credentials alone (a leaked connection string, an injection in the API, a mis-scoped replica login) can now, in one session that names a tenant: register any `(installation, repository id, name)`; write a map attestation in the name of any active human of the tenant; enable a repository; switch off every repository; **switch back on a repository that an operator switched off as an incident response**; and write the matching `repository.*` audit rows with any actor, which are indistinguishable from real ones. No MAC key is needed. The ADR's phrase "can enable a repository that has a map commit" (ADR 0016, revision note, "For the architect", item 2) is narrower than what the grants allow. Chained with the API's existing right to insert jobs and original requests, it also reaches the status writer (STS-1).
- **Judging the two designs.**
  - *Column grants as built.* Simple, atomic with the audit row when the API code is honest, and the database does enforce shape (CHECK, trigger, FK). It authenticates nobody: the principal that attests is a parameter the caller chooses (`up.sql:79-100` checks only that it is an active human of the tenant).
  - *Signed request, applied by the worker.* The API appends `repository.change_requested` with the existing key; the worker verifies, re-checks the designation of the numeric GitHub id against the protected allowlist at apply time (the R-4 rule the decisions already follow), applies through the Store, and records the result as `System`. This protects against a **database credential without the key**. It does **not** protect against compromise of the API process, because the process holds the key. It costs an asynchronous answer (202, then `show`) and a hook.
  - *`SECURITY DEFINER` function.* Gives atomicity (change and record in one call, so a credential holder cannot change a row without a record) and removes the table grants. It cannot authenticate the caller either, and it cannot check designations, which live in a protected file and not in the database. Alone it is a modest gain; next to the signed request it is not needed.
- **Recommendation.** Use the signed request for the three acts that **widen** the factory's reach (register, attest, enable), reusing `decision_signing.rs`. Give the worker the map-column grant it already has (`up.sql:103-106`, added "because the Store port is one trait"): in this design it is the right place for it. Keep **disable** direct, because narrowing is safe, and make the database enforce that with a `BEFORE UPDATE` trigger in the style of `audit_events_api_actions` that refuses, for a member of `factory_api_app`, any change except `enabled` from true to false. Correct `up.sql:32` and the T-38 residual, and write the remaining risk (API process compromise) down with an owner and a date.
- **Why the tests miss it.** `docs/database/tests/repository_map.sql` section 7 and `api_privileges.sql` check that the grants are exactly the listed ones and no wider. That is what the design says. No test asks whether a credential-only attacker should be able to widen the factory's reach, because that is the design question.

### REG-3. Registration trusts what the operator types (MINOR today; BLOCKER before a second tenant)

- **Evidence.** The body takes `installation_id`, `github_repository_id`, `full_name` and `default_branch` and checks their shape only (`apps/api/src/repositories.rs:78-86`, `328-403`); the API holds no GitHub credential (`repositories.rs:19-26`). The key is global on the repository id alone: `UNIQUE (github_repository_id)` (`migrations/2026-10-27-000200_tenancy_and_identity/up.sql:44`). The webhook lookup uses the pair and requires `enabled` (`migrations/2026-10-27-001400_rls_lookup_functions/up.sql:84-95`). There is no route and no grant to correct or remove a registration (the login has no `DELETE`, and no `UPDATE` on the ids).
- **Scenarios.**
  1. *Squat.* An operator of tenant X registers the id of a repository that belongs to someone else's installation, with any installation number. The real owner's registration is answered 409 for good, and only a database administrator can free the id. An honest typo of the repository id has the same effect on the id that was typed.
  2. *Oracle.* 409 versus 201 tells an operator of any tenant whether a given GitHub repository id is registered anywhere in the factory. The documents say so openly (`docs/guides/onboarding.md`, troubleshooting row), so I record it as known.
  3. *Mismatch.* Webhooks bind by the typed ids; every later act uses the typed name (`webhook.rs:250-262` records the issue as the registered name plus the payload's issue number, and `ask_for_a_reply` at `webhook.rs:310` carries the registered repository and that number). A label event on issue N of repository B can become a refusal reply or a job for issue N of repository A. The intake stage re-reads GitHub (AUT-11), which contains the job case. The refusal reply is not contained: the worker answers on the registered name.
- **What stops harm today (verified by reading).** (a) The credential for `(tenant, repository name)` comes from `github.installations` in the protected configuration (`external.rs:268-290`), and the token request names the repository and checks that the answer covers exactly it (`crates/github/src/token.rs:405-410`, `437-452`). A registration that points at a foreign installation therefore gives the factory no token. (b) A label from anyone who is not a registered, allowlisted requester of that tenant makes no job (`webhook.rs:199-207`). (c) One tenant.
- **So "harmless with one tenant"?** True for credentials and for authority. Not fully true for operations: scenarios 1 and 3 are possible with one tenant by mistake.
- **What a second tenant needs.** (1) An installation-to-tenant binding made by the installing person at install time and written by the platform, not typed by an operator. (2) Registration that asks GitHub, with an installation token: that the repository id exists, that its `full_name` and default branch are what GitHub says (store those, not the typed ones), and that the installation lists it. (3) A key on the pair, plus an unregister and transfer path under a platform designation. (4) The credential directory read from the verified binding, or intersected with it, so that the two sources of truth (the static list and the column `github_installation_id`) cannot differ unnoticed; today nothing compares them. (5) An answer that does not reveal whether the id exists elsewhere.
- **Why the tests miss it.** `repository_map.sql:217` and `apps/api/tests/repositories.rs:526` prove the intended exclusivity ("another tenant's repository cannot be registered"), which is the squat.

### REG-4. `show` skips the repository narrowing (MINOR)

- **Evidence.** `show` needs only `require_listed` (`apps/api/src/repositories.rs:406-413`). Every read of a job applies `require_repository` (`apps/api/src/reads.rs:151`, `270`, `403`); the three changes of this module apply `narrowed_away` (`repositories.rs:262-268`).
- **Scenario.** A person narrowed to one repository (API-1) who learns the identifier of another repository reads its installation number, GitHub id, map commit and attestor. Identifiers made by `derived` are not guessable, so the exposure is small.
- **Why the tests miss it.** The narrowing test covers register and the changes only (`apps/api/tests/repositories.rs:468-525`).
- **Fix.** Call `narrowed_away` after the read and answer 404.

### REG-5. A replay compares the name, not the request (MINOR)

- **Evidence.** The repeat check compares the audit event (`repositories.rs:272-278`). For a registration the event holds the new id and the name (`repositories.rs:362-371`) and not the installation, the GitHub id or the branch. `same_registration` in the store (`crates/storage/src/pg/jobs.rs:878-885`) compares all four, but it is reached only when the audit record is missing.
- **Scenario.** The same key and the same name with another installation number, repository id or branch is answered 200 `changed: false` with the first row. The module header promises "the same key with a different request is a conflict" (`repositories.rs:36-42`).
- **Why the tests miss it.** The replay test changes the name (`apps/api/tests/repositories.rs:703-760`).
- **Fix.** Put a digest of the whole body in the audit subject, or compare the stored row with `same_registration` on a replay.

### REG-6. The gate is a flag: one person, no consumer, no expiry (MINOR)

- **Evidence.** `git grep project_map` finds no reader of the commit or the attestor outside the store and the API. One person with both designations does all four steps in three calls (ADR 0016 revision note, "For the architect", item 1). The policy already has a precedent for a distinct-person rule with an opt-out (`policies/approval.yaml:168`, `approver_may_equal_requester_when_low_risk`). The table records no `enabled_by`. The attestor is checked when the commit is written (`up.sql:79-100`) and never again.
- **Scenario.** (1) An operator who is also an approver registers, attests the tip, enables; any later merge to the default branch changes the map and nothing notices. (2) The attestor is disabled as a principal; the repository stays enabled. (3) The attested commit may be ancestral to nothing the factory reads.
- **Fix.** A policy rule that the enabler differs from the attestor unless a single-maintainer flag is set for that repository; store `enabled_by` and `enabled_commit`; disable (or list in the health report) repositories whose attestor or enabler is disabled. The engine cannot read the map today, and the documents say so; the point is that the controls it does have should not weaken that statement further.

### REG-7. Migration facts (NOTE)

- Repositories that were enabled are switched off by the migration with a `NOTICE` and a version bump, but no audit record (`up.sql:41-53`). The audit chain is the only record of who changed what, and this change has no author in it. A deployment note, an audit row per tenant by a system actor, or both.
- The migration comment says the constraints are "added NOT VALID and then validated" (`up.sql:35`), and the safety guide says this "lets reads and writes go on" (`docs/database/migration-safety.md:189`). Inside one transaction the `ADD CONSTRAINT` lock is held to the commit, so the two-step form gives no benefit. Harmless on a small table; the sentence is inaccurate.
- A replayed request is compared with the audit event, which includes the policy hash (`repositories.rs:297`). After a policy change the same key answers 409 instead of repeating (`repositories.rs:272-278`).
- `down.sql` loses the attestations and does not re-enable what `up.sql` switched off; it says so.

### REG-8. Disable is not a stop (NOTE)

`disable_repository` drops webhooks and submissions and leaves jobs that exist untouched (`policies/approval.yaml:244`). The status step stops writing for that repository (`crates/composition/src/issue_status.rs:697`, `865-879`), so an issue keeps a stale `factory: working` label and never gets its last state. For an incident, `cancel_job` per job is still needed. Say so in the runbook.

### STS-1. Status is written for API jobs before intake accepts the issue (MINOR)

- **Evidence.** ADR 0017 says the worker writes "only for a job whose stored original request names an issue" (line 76) and that writing earlier "would let anyone who can forge a job row write on an issue of a registered repository" (decision 6, line 153). That holds for a job made by a webhook: its request row exists only after intake. It does not hold for `POST /v1/jobs`: the request is stored at submission with the caller's `source_ref` (`apps/api/src/jobs.rs:155-161`, `234-235`), and the only check is that the issue is in the job's own repository (`jobs.rs:184-195`). The step's `resolve` accepts any job that has a request, the same repository and an enabled repository (`crates/composition/src/issue_status.rs:680-710`).
- **Scenario.** A requester who may submit jobs, but holds no triage right on GitHub, submits a job for `owner/name#7`, an issue nobody labelled, or an issue of another person, or a pull request. The App writes `factory: queued` and "I have accepted this request" there, then, when intake refuses the job, `factory: rejected`. Because the stamp orders by start time, a second job on an issue that already has a running job replaces that job's comment (ADR 0017 decision 4). T-44 records that "a person who may submit jobs through the API can still make the worker write on the issues of the repositories they may use", so this is a known residual. What is wrong is the ADR text and the claim "accepted".
- **Why the tests miss it.** `a_job_with_no_original_request_has_no_issue_the_factory_accepted_and_gets_nothing` and `an_issue_in_another_repository_than_the_jobs_is_never_written_on` (`crates/composition/tests/issue_status.rs:710`, `718`) cover the two cases the rule names. None submits an API job for an issue that intake would refuse.
- **Fix.** Write only after the intake stage run has succeeded (that is where the label, its applier and the five-second rule are checked), or at least not for `RECEIVED`. Correct ADR 0017 section 5 and decision 6 to say which jobs the rule covers.

### STS-2. `Retry-After` is dropped, and the budget has no hourly bound (MINOR)

- **Evidence.** The adapter sleeps through a wait of at most 10 seconds and otherwise returns `RateLimited { retry_after }` (`crates/github/src/core.rs:97-129`, `BackoffPolicy` default at `46-62`). The step maps that to a code and discards the value (`issue_status.rs:176`), and retries after its own 30, 60, 120, 240 and 480 seconds (`issue_status.rs:451-454`, `769-788`). The bound is six updates a minute (`issue_status.rs:104`, `737`); there is none per hour. One update is about eight requests by my count: a mint, a comment list, a comment write, a label list, an add, a remove and a revoke, plus the first `GET /app`. The status writer shares the installation's budget with the stage tokens and never yields to them.
- **Scenario.** GitHub answers 403 with `Retry-After: 60`. The adapter does not wait (60 is over 10). The step retries after 30 seconds, which is **before** the 60 the host asked for, then four more times. T-44 itself says "an integration that keeps writing while it is limited can be banned". Sustained at the cap, 360 updates an hour is about 2900 requests, over half of a common hourly budget per installation. The secondary limits I recall from GitHub's documentation (a few dozen content-creating requests a minute and a few hundred an hour) are **unverified here**; the ADR says the page it read gave no numbers.
- **Why the tests miss it.** The adapter test proves "a short wait is honoured, a long one reported"; the step tests use a fixed 30 seconds (`crates/composition/tests/issue_status.rs:506-531`), and the only unit test of the mapping uses `RateLimited { retry_after: None }` (`issue_status.rs:1055`).
- **Fix.** Carry `retry_after` in the failure and set `not_before` to the larger of the two; share one "GitHub asked us to wait until T" gate between the status client and the stage clients; add an hourly cap; read `x-ratelimit-remaining` and pause the step when it is low.

### STS-3. "Newest wins" is list-then-write (MINOR)

- **Evidence.** The adapter lists the comments, compares the stamp, and then edits (`crates/github/src/status.rs:299-355`). GitHub has no conditional edit, and the one-second pacer is per process (`status.rs:78-104`). The label is written after the comment and carries no stamp (`issue_status.rs:841-858`). Nothing reads the issue again after the write.
- **Scenario.** Two workers (the step allows several) update the same issue for versions 5 and 6. Both list and see version 4. Worker 2 edits to 6; worker 1 edits to 5 a second later. The issue shows version 5 and the label of whichever wrote last. Both audit records say "written", the job is at its last version, and no later change exists to repair it. A one-process race is excluded by the single delivery task.
- **Why the tests miss it.** `when_two_updates_race_the_newer_version_stays_on_the_issue` (`crates/composition/tests/issue_status.rs:650`) races against the fake in an order the fake allows; the fake has no interleaving between list and edit that a real network has (unverified, I did not read the fake's routes).
- **Fix.** After a write, list once more and repair if a lower stamp is shown; or serialise per issue with a database advisory lock taken through the store for the length of the write.

### STS-4. The session is spared by a snapshot, and the entry has no guard (MINOR)

- **Evidence.** The sweep copies the set of running jobs first (`crates/composition/src/token_sweep.rs:72`), then lists open jobs from the database, then revokes every live token whose job is not in the copy (`token_sweep.rs:118`, `crates/github/src/token.rs:523-544`). The status round enters its session and mints afterwards (`issue_status.rs:834-835`). It leaves after the revoke (`issue_status.rs:860-861`) with no `Drop` guard (`crates/composition/src/indexing.rs:51-62`).
- **Scenario.** (a) A round that starts in the milliseconds between the sweep's copy and its revoke has its token revoked and its session marked ended; the next call is `Unauthorized`, the code is `Interrupted`, and the update retries after 30 seconds. Noise, no harm; the code is named for it, so the author saw it. (b) A panic in a call, or the task dropped at shutdown, skips `leave`. The session then stays in `ActiveJobs`, the sweep spares it for the life of the process, and its `issues: write` token for one repository lives until GitHub expires it (at most an hour; I did not check the exact lifetime). It cannot be reused for another round because the session is fresh.
- **Why the tests miss it.** `each_round_uses_a_fresh_session_that_the_sweep_spares_and_that_is_ended_afterwards` (`issue_status.rs:769`) runs the sweep while the round is already in progress and to completion.
- **Fix.** Make `enter` return a guard that leaves on drop and revokes in a `spawn`ed cleanup; take the `running()` copy after the database listing, or pass the sweep a closure.

### STS-5. The label type is strong; its test-only escape hatch is only a scan (MINOR)

- **Evidence.** `StatusLabel` has private fields, no `Deserialize`, no `Default`, no `From`, and `unsafe_code = "forbid"` is set for the workspace (`Cargo.toml:16`). `StatusLabels::label_for` and `IssueWorkflowPolicy::status_labels` are the only producers (`crates/domain/src/policy/issue_workflow.rs:327-350`, `627-660`). The one exception is `pub fn forged_for_negative_tests` (`issue_workflow.rs:300-311`), reachable from any crate. Its callers are `crates/testkit/src/contracts/issue_status.rs:255`, `crates/github/tests/issue_status.rs:252` (a crate that is not on the rule's list, in a test directory) and a unit test in the same module (`issue_workflow.rs:708`). The rule is `docs/architecture/crate-dependency-rules.json:777-782`, enforced by `xtask/src/static_checks.rs:593-648`. That scan flags a path only when it is followed by `(` (`static_checks.rs:606`), skips test-support crates, and does not read `tests/` directories. `.map(StatusLabel::forged_for_negative_tests)` is not followed by `(`. `git grep` finds no fixture that makes the new rule fire.
- **Second gap.** The type excludes the trigger label of `issue-workflow.yaml`. The engine acts on `intake.trigger_label` of `approval.yaml` (`crates/domain/src/policy/approval.rs:424`, `policies/approval.yaml:370`). The documents say the two must be equal; only the Python tool checks it. No Rust code compares them.
- **Impact.** None today: no production call, and `testkit` is a dev-dependency in the four `Cargo.toml` files that matter here (`composition`, `github`, `api`, `worker`); I did not check the others. If a call did appear, the webhook would still refuse a trigger label whose sender is the App (`webhook.rs:199-207`, `267-300`), and the Action reverts unknown writes.

### STS-6. The policy hash is dropped, and two approval rows are decoration (MINOR)

- **Evidence.** `load_issue_workflow` returns a hash (`crates/composition/src/startup.rs:108-141`) that nothing reads. The step records the combined hash of the security and approval documents (`apps/worker/src/pipeline.rs:263`, `startup.rs:92-94`). `git grep` finds no code that reads the rows `write_status_label` or `close_or_label_issue`. The only runtime switch is `github.write_issue_status`.
- **Impact.** An `issue_status.*` audit row cannot say which label map was in force. An architect who edits `write_status_label` to `requires: human` would stop nothing.
- **Fix.** Include the issue workflow hash in the recorded policy hash, or in the reason; mark the two rows "documentation" or make the step ask the engine.

### STS-7. A missing policy file stops the worker (MINOR)

- **Evidence.** `issue_status(...)` returns an error when `policies/issue-workflow.yaml` cannot be loaded, and `main` prints it and exits with code 1 (`apps/worker/src/main.rs`, diff; `apps/worker/src/pipeline.rs:246`). The key defaults to on (`crates/composition/src/config.rs`, `default_true`).
- **Scenario.** The worker is upgraded before the protected checkout carries the new file, or the file has a typo: no job is processed at all. This is fail-closed for the labels and a hard stop for the work, against ADR 0017: "A job must never wait for, fail on or roll back because of a label."
- **Fix.** On a load failure, switch the step off, report `degraded`, and keep working. Or default the key to off until the file exists.

### STS-8. The repository is compared with and without case (MINOR)

- **Evidence.** The API accepts a `source_ref` whose repository equals the registered name without case (`apps/api/src/jobs.rs:190-195`). `resolve` does the same (`issue_status.rs:697-702`). The adapter then requires `scope.repo == issue.repo` with `RepoRef`'s derived, case-sensitive equality (`crates/github/src/status.rs:141-143`, `crates/ports/src/paths.rs:492`).
- **Scenario.** `Octo/Hello#7` for a repository registered as `octo/hello`: the job is accepted and the status write is `NotFound` on every try. Fails closed; no status is ever shown.
- **Fix.** Build the `IssueRef` from the registered repository, or compare in one canonical form everywhere.

### STS-9. Sharp edges (NOTE)

- A thread over 1000 comments (10 pages of 100, `crates/github/src/client.rs:34-41`) that gets its first status comment late is `Unavailable` forever, and because the comment comes first (`issue_status.rs:841-851`) the label is never written either.
- The step's in-memory maps are keyed by job id alone (`issue_status.rs:324-338`). A holder of the API database credential can insert a job in tenant B with the id of a job in tenant A and mix their progress. Observability only.
- One budget for all tenants and a queue ordered by job id (`issue_status.rs:724-748`): a flood in one tenant delays the others' status. T-44 says "across all tenants".
- After a disable, an issue keeps a stale label (REG-8). The Completed text promises a draft pull request (`issue_status.rs:266-271`); I did not check that every completed job has one.

### STS-10. Unverified against the real GitHub (NOTE)

## 4. Answers to the eleven questions

**1. Registration across tenants (A). Verdict: possible, contained today, not safe for a second tenant.** An operator of tenant X can register any installation number, repository id and name that no earlier registration holds (`repositories.rs:328-403`). Nothing looks at GitHub. Real webhooks of that installation would bind to X if the pair matches and the row is enabled (`migrations/2026-10-27-001400_rls_lookup_functions/up.sql:84-95`). What stops harm: the credential comes from the static list, not from the row (`external.rs:268-290`), and the token's answer must cover exactly the named repository (`token.rs:437-452`); the sender must be a registered, allowlisted requester (`webhook.rs:199-207`); intake re-reads GitHub. "Harmless with one tenant" is true for credentials and authority and not for the squat, the mismatch and the oracle (REG-3). A multi-tenant deployment needs a verified installation-to-tenant binding, registration that stores GitHub's own values, a key on the pair, an unregister path, and one source of truth for the credential.

**2. The API login's write grants (A). Verdict: weaker than the project's pattern; recommend the signed request for widening acts.** REG-2 has the full judgement. In short: compromise of the API process or of its database credential now allows registering, attesting under any person's name, enabling, undoing an operator's disable, and writing the matching audit rows. A signed request protects against a credential without the key and not against the process. A definer function gives atomicity and removes grants, but cannot authenticate the caller or check designations. Do the signed request for register, attest and enable; keep disable direct and database-enforced as narrowing only.

**3. Attestation and enable (A). Verdict: finding REG-1 and REG-6.** After enable, a new attestation replaces the commit and the attestor and leaves `enabled` true (`jobs.rs:982-1022`). There is no time-of-check/time-of-use check because the attested commit has no consumer: stages read whatever the default branch holds at the base commit of the job, and nothing compares it with the attestation. An attestor who is also the enabler weakens the control; no rule forbids it and the ADR asks the architect. A forged or foreign principal: through the API, no (the principal is the token's; the trigger requires an active human of the same tenant, and the foreign-key includes the tenant). A holder of the database credential can name any active human of the tenant (REG-2). The check is made when the commit is written; a principal disabled later keeps the attestation valid.

**4. Idempotency and audit (A). Verdict: sound, with REG-5.** The derived id hashes tag, tenant, caller's principal, subject and key (`repositories.rs:106-120`). The key is the last field, so no choice of key can move a boundary. A different caller or tenant gets a different id (a unit test pins this, `repositories.rs:581-603`). The chain cannot be forked or skipped through the API: the sequence, previous hash and hash are assigned by the database under a per-tenant advisory lock (`migrations/2026-10-27-000700_audit_events/up.sql:96`), and the API login can insert and nothing else. The change and the record share one transaction (`repositories.rs:458`, `514` then `317-324`); a lost answer is settled by the witness. What can happen is a change **without** a record, but only for a database-credential holder, because the update grant stands alone (REG-2). Replays: REG-5 and REG-7.

**5. Label forging (B). Verdict: no production path; the rule is a scan with limits.** `forged_for_negative_tests` is the only way to make a `StatusLabel` outside the policy; there is no constructor from text, no `Deserialize`, no `Default`, no `From`, no public field, no `unsafe` (forbidden for the workspace), no `transmute` in the module. Callers are in `testkit`, a test directory of `github` and a domain unit test. The ST-13 rule can fail, but only for a direct call from non-test source (STS-5). The adapter re-checks with `check_status_label_name` before any request, including the one for a token (`status.rs:226-227`): the prefix `factory: ` is matched case-sensitively, the name must be printable ASCII (so no Unicode look-alike and no tab), at most 50 characters, and no space at the edge (`issue_workflow.rs:260-277`). Removal uses an ASCII case-insensitive prefix and a character-boundary-safe slice, so a name with a multibyte character at the boundary is left alone (`status.rs:258-260`). Duplicate names in the policy are rejected after lower-casing (`issue_workflow.rs:431-444`).

**6. Token (B). Verdict: as designed, with STS-4.** The request is `metadata: read` and `issues: write` for one repository name (`permissions.rs:104-113`, `token.rs:405-410`). The answer is checked: exactly one repository whose `full_name` matches, and no permission outside the request, or the token is revoked at once and refused (`token.rs:437-452`). The stage sets are unchanged in the diff. The cache key holds class, repository and permission set, per session; the session is a fresh UUID per round, the installation is looked up by `(tenant, repository)`, so a token cannot cross tenants, repositories or rounds. It lives for the round (seconds to a few minutes) and at most the hour GitHub gives. It is revoked by `DELETE /installation/token` after the round (`issue_status.rs:860`); a failed revoke is kept in `leftovers` and retried by the sweep (`token.rs:498-517`, `523-544`). The spared session can leak a live credential only for the life of the process after a panic or a cancelled task (STS-4).

**7. Comment content and the marker (B). Verdict: no untrusted text reaches the comment or a label name.** The text is a closed template (`issue_status.rs:241-280`); the only variable pieces are a state, a stage phrase, the registered `owner/name` (letters, digits, `_`, `.`, `-` only) and the branch derived from the job id. The label name comes from the loaded policy. No GitHub error string is stored: failure rows carry a fixed word (`issue_status.rs:893-903`). The text passes the secret check and the Markdown cleaning twice (`crates/github/src/text.rs:95-106`) plus a second secret check in the step (`issue_status.rs:816-823`); the marker is added after the cleaning (`status.rs:285-287`). "The App's own" is decided by `user.login` equal to `<slug>[bot]` read from `GET /app` (`status.rs:186`, `292`; unverified against GitHub). A person cannot post as that login (unverified: it relies on GitHub reserving the `[bot]` suffix), and a pasted marker is ignored. The stamp is parsed only in the exact written form and the last marker counts (`crates/ports/src/issue_status.rs:89-107`). A person who can edit the App's comment can plant a future stamp and freeze it (T-43 residual, accepted).

**8. Tenant isolation and confused deputy (B). Verdict: isolation holds; the "accepted issue" claim does not (STS-1).** The step reads under the worker's tenant pool, `TenantScope::new(tenant)` for each served tenant (`apps/worker/src/pipeline.rs:241-244`, `issue_status.rs:472`), under the worker login and row-level security. It reads no other tenant. It cannot write to another repository: `resolve` demands the issue's repository equals the job's (`issue_status.rs:694-703`), the adapter checks again (`status.rs:141-143`) and the token is minted for the scope's repository. It can write on any issue number of the job's own repository for an API job. The reasoning "a webhook job before intake is skipped" is sound for webhook jobs. It does not cover API jobs, nor a holder of the database credential, who can insert both the job and its request. The `enabled` check is applied twice (`issue_status.rs:697`, `865-879`). A disabled tenant is not checked.

**9. Failure behaviour (B). Verdict: bounded; two weaknesses.** No redirect is followed (`ureq_transport.rs:48`), bodies are cut at 4 MiB (`ureq_transport.rs:23`), a call times out at 30 seconds (`ureq_transport.rs:50`), the blocking client runs in `spawn_blocking` (`ureq_transport.rs:126-131`), a 5xx is retried only for GET (`core.rs:115-126`), pagination stops at 10 pages and a `Link` to another host is not followed (`client.rs:236-276`). Retries per call: 3; tries per version: 6; delivery per task: 20; pending entries: 1000. Nothing loops forever and nothing in the code I read panics on hostile input. A stalled GitHub holds only the delivery task. Weaknesses: the retry schedule and budget (STS-2) and the lost update (STS-3).

**10. Policy loader (B). Verdict: fail-closed, with gaps in the audit binding.** It reads one fixed path under the protected checkout and refuses a checkout inside an untrusted root (`crates/contracts/src/policy/issue_workflow.rs`, `startup.rs:123-141`). The loader is strict: one document, `schema_version` first, unknown fields denied at every depth, and `problems()` must be empty. A project-local file cannot override it: the checkout is the factory's own. A missing or broken file stops the worker (STS-7). The hash is computed and dropped (STS-6).

**11. Migration safety (A). Verdict: safe, with REG-7.** The `NO FORCE` and `FORCE` pair is the documented pattern (`docs/database/migration-safety.md:88`), Diesel runs each migration in one transaction (`migration-safety.md:55`), the `ALTER` takes an `ACCESS EXCLUSIVE` lock that is held to the commit, and `lock_timeout` is 5 seconds (`up.sql:37`). A failure rolls the `FORCE` back to its old state. Even if someone ran the file outside a transaction, only the table owner (not an application login) would bypass the policy. `down.sql` restores the previous audit function (its list is identical to `migrations/2026-10-29-002200_api_stage_decision_action/up.sql:20-25`), revokes all ten column grants and the worker's two, drops the trigger, function, constraints and columns, and sets the default back to true. I see no privilege left behind. It does not re-enable repositories and loses the attestations, as it says. Not run.

## 5. What held

- The API login's grants are column-exact, and the suite checks both ways, including that a registration cannot say enabled, a ceiling, a protection result or a map, and cannot name another tenant (`repository_map.sql:201-230`).
- The attestor must be an active human of the tenant, checked in the statement, the trigger and a foreign key that includes the tenant (`jobs.rs:982-1022`, `up.sql:79-100`).
- The roles are read from the approval policy and a missing row means no role and a 403 (`apps/api/src/decisions.rs:133-148`).
- The reasons are length-bounded, clean text, and checked for secrets with a fail-closed redactor (`repositories.rs:152-165`).
- The status token cannot be wider than asked: the answer is verified and the token is revoked on a mismatch.
- The adapter refuses a wrong label before it asks for a token.
- The comment is found among the App's own comments only, and a cut listing is an error and not a second comment.
- The worker never waits for the writes: the hook spawns one task and returns.

### REG-2 after the fix (2026-11-03)

**What changed.** Register, attest and enable are signed requests. The API checks the designation and the narrowing, appends one `repository.change_requested` record signed with the decision key (`crates/composition/src/decision_signing.rs`, a context line of its own) and answers `202`. The worker step `RepositoryChanges` (`crates/composition/src/repository_changes.rs`, wired into the hook before each claim) verifies the word before it reads anything else, checks that the person is an active human principal of the tenant, asks the protected allowlist again by the numeric GitHub id (the R-4 rule), with the repository's GitHub id (RR-28), applies the change through the Store and writes the result as `System` in the same transaction; the result id is a keyed function of the request id, so a request is applied once. `GET /v1/repository-changes/{request_id}` reports `requested`, `applied` or `refused` with a fixed code; `factory-cli repository register | confirm-map | enable` wait up to 60 seconds for it (`--wait-seconds`) and `repository change` looks again. Disable stays direct. Migration `2026-11-03-002700` takes the API login's INSERT and map-column UPDATE grants away (it keeps `UPDATE` of `enabled` and `version`), takes `repository.registered`, `repository.map_attested` and `repository.enabled` out of the audit actions the API may write, adds `repository.change_requested`, and adds the `BEFORE UPDATE` trigger `repositories_api_may_only_disable`, in the style of `audit_events_api_actions`, that refuses for a member of `factory_api_app` any change of a repository except one that sets `enabled` to false (the whole row is compared). The worker's group already held the map-column grants ("because the Store port is one trait"), so none was added. The sentence "the same limit holds for the decision requests" is corrected in the comment of migration `2026-11-02-002400` and in threat T-38, and the residual risk is written in ADR 0016 with an owner and a date.

**Residual risk, accepted.** A signed request protects against a holder of the API database credentials who does not hold the key. It does not protect against a compromise of the API process, because the process holds the key; such an attacker signs any request, and the worker applies it only as far as the designation of the active person it names allows, re-checked at apply time. The key is shared with the worker (AUT-12), so a compromised worker can sign too. **Owner: the project owner. Written down on 2026-11-03. Reviewed again when a second tenant is onboarded, when the key leaves the API process, or by 2027-05-03.**
