# Security review of the registration hardening of 2026-11-03 (REG-6, RR-28, REG-2)

- Reviewer: an independent security reviewer (Claude Sonnet 5.5), working alone from the repository. I wrote none of the code under review and changed none of it. My only addition is this document. (To print three booleans I added one scratch test to `crates/domain/tests/policy/authority.rs`, ran it and reverted it with `git checkout`; no commit holds it.)
- Date: 2026-11-03. Reviewed commit: `1b65bbf` (`feat/slice-0-foundation`, "Merge repository registration hardening (REG-6, RR-28, REG-2)"). The worktree was at the first commit and was fast-forwarded to it.
- Question: (A) can the registration path as it is now built (migrations `2026-11-03-002600` and `002700`, the signed `repository.change_requested` requests, the worker step `RepositoryChanges`, the `BEFORE UPDATE` trigger, `single_maintainer`, the narrowing of the allowlist by GitHub's repository id) be used to widen the factory's reach, by a holder of only the API database credentials, by a replayed or late request, or by a person who holds a designation narrower than the act; (B) did the new design reopen or worsen REG-1, REG-3, REG-5 or REG-8 of `engine-registration-and-status-security-review.md`.
- Environment: a mix, and each statement says which. **(run)** means I executed it against PostgreSQL 18.6 (a private cluster made by `scripts/db-test.sh`, real `LOGIN` roles with the group memberships of production) or against `cargo test`. **(read)** means I read the code and did not run it. I did not build `factory-composition`, the API or the worker, and I did not run their test suites, so everything about the Rust worker step is **read**, except where a SQL probe reproduces the statement the worker sends. Nothing ran against a real GitHub.

## 1. Verdict

**PASS WITH CONDITIONS.** I found no BLOCKER.

The question I pushed hardest was whether a holder of **only** the API's database credentials can widen the factory's reach. They cannot, in any of the ways the question lists (run, section 4): not register, not attest, not enable, not change `single_maintainer` or `enabled_by`, not switch back on a repository an operator switched off, not write the records of a result. A signed request cannot be made, copied to another tenant or another actor, or changed after signing by someone without the key (read, with the word's coverage checked line by line). The comparison of the word is constant time and its context line is its own (read). The worker asks the protected allowlist again by the numeric GitHub id, and an allowlist that is missing or unreadable ends in a refusal, never in an application (read). The rule "the enabler is not the attestor" holds in the table for two sessions that race (run, three races) and in the Rust statement (read).

**Why not PASS.** One MAJOR and several MINOR.

1. **RH-1 (MAJOR).** A signed request has no expiry and a disable does not cancel it. The decisions of people expire after the approval window and say so (`decisions.rs:1364`); the repository requests copy the signature and not the expiry, while the key rotation runbook tells the operator that a request older than the 72-hour approval window is rejected, in a runbook whose first paragraph counts the repository requests among the requests the key signs. A request that waits (a worker that is down, a migration rolled back and applied again) is applied when the worker next runs, **also to a repository that an operator switched off in between**. This is the incident-response case the question asked about, reached through the legitimate path and not through the database. It is cheap to close.
2. **RH-2 and RH-3 (MINOR).** RR-28 closed the hole of the name by opening the converse one at registration (a person narrowed to one repository id can register that id under any name), and the design approver, whose approval is a GitHub label judged only inside the intake stage, is still narrowed by name. The ADR calls the stages "a second, conjunctive check"; for the design gate they are the only check.
3. **RH-4 to RH-7 (MINOR).** The exactly-once claim holds in the normal path and not at the edges (two workers with an operator's disable between them; a key rotation; a log longer than 10,000 records). The API login can still write `repository.disabled` audit rows attributed to the system or to anyone. `single_maintainer` is chosen by the role it constrains. A second `enable` of an enabled repository is applied and recorded as the second person's act while the table keeps the first.

**Conditions.** Close RH-1 before the first real repository is enabled. Correct the claims listed in RH-11 before the documents are used as a statement of what the system does (the rotation runbook is wrong in a way that matters to an operator). Close RH-5 or accept it in writing. RH-2 is a hard precondition of a second tenant (it is the same class as REG-3, which already is). RH-3, RH-4, RH-6, RH-7 and RH-9 can follow in the next round. RH-8, RH-10, RH-11 and RH-12 are notes.

**What the verdict does not cover.** Everything that needs the real GitHub; a deployed worker with a key and an allowlist; the Rust test suites (not run); the compromise of the API process or the worker, which hold the key and which the project owner accepted on 2026-11-03.

## 2. Severity scale

BLOCKER: do not use against a real GitHub, or by anyone but the builders, until closed. MAJOR: a control the documents promise is weaker than promised, or a party can reach further than its designation, and the fix is cheap before wider use. MINOR: defence in depth, a wrong reason, an inaccurate claim, observability. NOTE: worth knowing, no action needed now. There is no BLOCKER.

## 4. Answers to the questions

**1. Can a holder of only the API's database credentials widen the factory's reach?** No, with one thing to record. I connected as a real `LOGIN` role that is a member of `factory_api_app` and `factory_resolver` and of nothing else (session user and current user the same, as in production), named tenant 1 by hand, and tried each act (run, `rh_api_probe`):

| Act | Result |
|---|---|
| Register: `INSERT INTO repositories (...)` with any installation, id and name; and `INSERT ... ON CONFLICT DO UPDATE SET enabled = true` on an existing row | `permission denied for table repositories` (both) |
| Attest: `UPDATE project_map_commit`, `UPDATE project_map_attested_by_principal_id` | `permission denied` (both) |
| Enable: `UPDATE repositories SET enabled = true` on an attested repository that an operator had switched off | `ERROR: the API login may only switch a repository off` (trigger, SQLSTATE 42501) |
| Enable naming the enabler (`enabled_by_principal_id`, `enabled_project_map_commit`) | `permission denied` |
| Change `enabled_by_principal_id` on an enabled repository | `permission denied` |
| Change `single_maintainer` | `permission denied` |
| Off and then on in one transaction | the first statement `UPDATE 1`, the second refused by the trigger |
| Switch a repository off | `UPDATE 1`; the record of the enabling is emptied by the table |
| Write audit rows `repository.registered`, `repository.map_attested`, `repository.enabled`, `repository.change_refused` as the system | all four refused: `the API login may not write an audit record with this action or this actor` |
| **Write an audit row `repository.disabled` as `system` / `worker.repository`, or as a person** | **accepted** (RH-5) |
| Write an unsigned `repository.change_requested` row as a person | accepted; the worker ignores it (read), the status route reports it as `requested` (RH-5) |
| `SET ROLE factory_app`, `SET session_replication_role = replica`, `ALTER TABLE ... DISABLE TRIGGER`, `CREATE OR REPLACE FUNCTION` over the guard, `DELETE`, `TRUNCATE` | all denied |
| Name tenant 2 and switch its repository off | `UPDATE 1` (RH-10) |

Replay and reorder need the key (read): the word covers the tenant, the person, the id of the audit record, the time, the kind, the repository, the commit or the ids, `single_maintainer` and the digest of the detail text (`decision_signing.rs:369-379`, `repository_changes.rs:199-262`); the database assigns the sequence under a per-tenant advisory lock (`audit_events_assign`), so the order of the log is the order of commit and cannot be chosen; the event id is unique per tenant. The credential holder therefore has these effects: disable (RH-10), forged audit rows (RH-5), and junk that costs the worker one HMAC each (RR-21, not new).

**2. Can a signed request be replayed after its repository changed, applied twice, applied for another tenant, or by a worker that does not hold the allowlist? Is the MAC context-separated? Constant time?**

- *After the repository changed:* not by someone without the key. By time, yes: RH-1. The commit check (REG-1) is the only state the request binds.
- *Twice:* not in the normal path; at the edges, yes: RH-4.
- *Another tenant:* no. The tenant is in the word, the scan and the transaction are per tenant, and a request that names another tenant's repository finds `NotFound` under row-level security and is refused as `not_found` (read).
- *A worker without the allowlist:* it cannot apply. `FileAllowlist::entries` returns `Unavailable` when the file is missing, too large or does not parse (`seams.rs:312-327`), the authority maps that to `Unreadable`, and the step answers `Later` (read). After `MAX_TRIES` = 20 passes the request is refused as `not_settled` and recorded (`repository_changes.rs:483-492`, `decisions.rs:120`). It fails closed, at the price that a person must ask again after a long outage.
- *Context separation:* `factory-repository-change-request/1` is the first line of the message and no other message starts with it; the three keyed ids have contexts of their own (`decision_signing.rs:91-126`, `:369-379`). The key is shared with the decisions (accepted, AUT-12), so the separation is the context line and nothing else. No test asks that a word made for a decision, a dependency decision, a stage decision or a rejection does not verify as a repository change, or the reverse (the tests of the step cover no word, a wrong key, a changed detail and another actor).
- *Constant time:* `verify_message` computes the expected word under each key, **always both**, and combines them with `subtle`'s `ct_eq` on 32 bytes (`:622-632`). A word that is not 64 lower-case hex digits returns early, which reveals the shape of the word and nothing else.

**3. Does the worker re-check the designation of the numeric GitHub id at apply time? Missing or unreadable allowlist?** Yes. `apply_in` reads the principal from the database by the id in the signed record, requires an active human, takes the **GitHub id from the principal row** and not from the text (`repository_changes.rs:545-552`), then asks `permits(tenant, github_user_id, action, identity)` (`:587`) with the designation the `actions` table names. The allowlist file is read on every call (`seams.rs:251-266`). An action with no row in the table, or a row whose role names are all unknown, gives an empty set and a refusal (`decisions.rs:495-505`). Missing or unreadable file: `Later`, then `not_settled`. The one thing that is not re-checked at apply time is the shape of the typed name and branch (RH-12).

**4. Does REG-6 hold under races and on both paths? Can `single_maintainer` be set after registration?** The rule holds in the table and in the Rust statement.

- *Table (run).* Three races between two real sessions of the worker group on the same row, raw SQL with no version guard so that only the table's own rules are exercised:
  X, attest by A (holds the row three seconds) against an enable by A that was valid when its author read the row (the attestor was B): the enable waits, then the trigger refuses it with `the person who enables a repository must not be the person who attested its project map`; final state disabled, attestor A.
  Y, enable by A (valid, the attestor is B) against attest by A of the same commit: the attest moves the attestor to A, and because the repository was enabled the trigger switches it off; final state `enabled=false`, enabler empty, never "enabled by its attestor".
  Z, attested by A; enable by B holds the row against a raw enable by A: the second statement is accepted as a no-op and the record stays with B. No pair is ever stored.
  READ COMMITTED re-evaluates the trigger on the newest version of the row after the lock wait, which is why these hold.
- *Rust (read).* `enable_repository` carries the rule in its `WHERE` (`single_maintainer OR attested_by IS DISTINCT FROM $5`), the version guard, the commit guard and the active-human test (`jobs.rs:1111-1152`); a zero-row result is read back and mapped to `EnablerIsAttestor`, `ProjectMapChanged` or `Conflict` (`:1017-1063`); `attest_project_map` has no enabler rule and does not need one, because a changed attestor on an enabled repository switches it off in the table.
- *One principal per human.* `principals` has `UNIQUE (tenant_id, github_user_id)` (`2026-10-27-000200_tenancy_and_identity/up.sql:64`), so the "one human, two principals" gap noted in the fix status of REG-6 needs two GitHub accounts.
- *The flag after registration.* No route: the body of `register` is the only place (`repositories.rs`, `RegisterBody`), the API login lost its `INSERT` grant on the column in `002700` and never had `UPDATE`, the worker group has no `UPDATE` on it, and the trigger refuses a change by a member of either group even if a grant were given (run, `repository_map.sql` 11b, which passed). A replay of a registration with the other flag is `id_reused` -> `conflict` (`jobs.rs:920-928`). The table owner and a superuser can change it (documented). Who may **choose** it at registration is RH-6.

**5. RR-28: any path that still narrows by name where an id exists? Case, Unicode, transfer, an entry with another repository's id and this one's name?**

- *Paths by name.* The stages of the workflow crate (`AuthorityPolicy::designations`, `authority.rs:1066`): the requester check at intake (`handler.rs:200`) and the design approver (`design.rs:267`); the apply-time re-check of dependency decisions and stage decisions (`dependency_decisions.rs:547`, `stage_decisions.rs:641-643`). The first two are in RH-3. The registration, where the name is what the operator typed, is RH-2.
- *Case.* `eq_ignore_ascii_case` on the whole `owner/name` (`authority.rs:179-186`); the existing test covers `ACME/OLD-NAME`.
- *Unicode.* The API accepts `[A-Za-z0-9_.-]` only (`repositories.rs`, `is_full_name`; its test refuses `e-acute/x`) and the table has the same `CHECK` (`000200_tenancy_and_identity/up.sql:31`). An entry in the allowlist file that carries a confusable character never equals a registered name, because the fold is ASCII only, so it grants nothing: it fails closed. The loader does not warn about it (a typo grants nothing and says nothing).
- *Transfer and rename.* There is no route that changes `full_name` (the API test edits it with SQL as the owner, `apps/api/tests/repositories.rs:1945` and `:1960`). The first layer follows the id. The stages keep matching the **registered** name, which does not move, so they keep working after a rename and keep matching a new repository created under the old name.
- *An entry with the id of another repository and the name of this one* (run, scratch probe in the domain test): the first layer says not covered, and the stage layer says **covered** (RH-3). The converse, the id of this repository and a different name, is covered by the first layer and refused by the stage; that case does not occur in practice because the registered name never changes.

**6. Migration safety.** See RH-9. The suites passed (run): `repository_map`, `api_privileges` and `privileges` (289 checks) and `migrations` (28 checks: up, revert all, up, redo, and revert-and-run of the j newest for every j from 1 to 27, with an identical catalog fingerprint each time).

## 6. Findings in detail

### RH-1. A signed repository request never expires, and a disable does not cancel it (MAJOR)

- **Evidence.**
  - `Pending` holds the id, the correlation, the person, the fields, the detail and a failure count, and no time (`repository_changes.rs:291-300`). `request_from` uses `requested_at` only inside the word check (`:425-456`). `apply_in` has no test of age (`:531-640`). The time is in the signature (`decision_signing.rs:369-379`), so the information is there and unused.
  - The decisions of people do test it: "a request that has waited longer than the approval window is rejected, never applied late (R-11)" (`decisions.rs:1364-1370`; the same in `dependency_decisions.rs:442`). The header of `002700` says it makes the statement true "by moving the acts that WIDEN the factory's reach, register, attest and enable, onto the same path", and the rotation runbook says "the approval window: 72 hours. A request older than that is rejected" (`docs/runbooks/rotate-the-decision-key.md:14`, "Before you begin") in a document whose "Symptom" paragraph counts "a request to register, confirm or enable a repository" among the requests the key signs.
  - A disable is a direct write that records `repository.disabled` (`repositories.rs:632-642`). The step reads that action nowhere: it matches only `REQUESTED` and the four ends (`repository_changes.rs:395-411`).
  - Nothing lists the requests that wait. `GET /v1/repository-changes/{id}` needs the id (`routes.rs:255`), the fix status of the earlier review says there is no list of requests (`engine-registration-and-status-security-review.md`, section 8, "REG-2 after the fix", item 2), and there is no cancel. The incident runbook was written before the signed requests and does not mention the worker or a pending request (`docs/runbooks/stop-work-on-a-repository.md`: a search for `pending`, `signed request`, `worker` and `repository-changes` finds nothing).
  - The request names the commit and does not name the state of the repository the person saw (disabled or enabled, version). The commit is the only thing the store checks (`jobs.rs:1122`).
- **Scenario (read; the Rust step was not run).**
  1. Repository X is attested at commit C1 by A. Approver B asks to enable it; the API answers 202. The worker is not running (a deploy, a crash, or stopped as the first move of an incident).
  2. The operator freezes the factory and disables every repository. X is already off; the operator believes it is frozen. (Variant: B enabled X, a second approver filed another enable for X before the incident because RH-7 lets the API accept it, the worker settles ten requests per pass, and the operator disables X while the second request still waits.)
  3. The worker starts. B still holds `approver` on the allowlist, C1 is still the attested commit: the step enables X. Webhooks bind again, jobs start.
  Nobody decided after the incident that X may take work. The same holds for a stale `attest`: it moves the map back to an old commit and, if X is enabled, switches it off. A second route: the `down.sql` of `002700` leaves the unsettled requests in the log ("harmless"), and when the migration is applied again with a new worker they are applied whatever their age.
  What limits it: B must still be an approver when the worker runs (the incident that removes B from the allowlist stops it), and REG-1 holds (a changed map refuses it).
- **Fix recommendation.**
  1. Refuse a request older than a fixed window, from the signed `at=` text against the clock the worker already has, with a recorded refusal `expired`. Use the approval window (72 hours) at most; a request that a person made at a terminal and expects to be settled in a minute can be much shorter (15 minutes).
  2. Bind the act to the state the person saw, as a decision is bound to the head: sign the `version` of the repository that the API read (it reads the row already, `repositories.rs:605-612`) and refuse an `enable` or `attest` when the version moved for any reason other than the request's own predecessors. A disable then cancels every waiting request of that repository by moving the version. If a signed version is more than you want to build now, refuse an `enable` when a `repository.disabled` record of this repository has a greater sequence than the request.
  3. List the waiting requests (`GET /v1/repository-changes?state=requested`, operator) and let an operator cancel one.
  4. Correct the rotation runbook sentence and add "stop the worker or list and cancel waiting requests" to `stop-work-on-a-repository.md`.
  5. Also require a fresh attestation after a disable (the second half of REG-1): clear the attestor on disable, or compare the age of `project_map_attested_at`.
- **Why the tests miss it.** `a_request_is_applied_once_whatever_the_number_of_passes_and_workers` runs passes back to back (`crates/composition/tests/repository_changes.rs:361-391`). No test lets time pass or disables the repository between the request and the pass. The seven breaks in `apps/api/tests/mutations/repository_change_breaks.py` are: no word check, no digest check, no second allowlist question, a person switched off since, the name alone, no result written, a conflicting repeat. None is age or state.

### RH-2. The narrowing by id leaves the typed name free (MINOR; hard precondition of a second tenant)

- **Evidence.** A listing with an id compares ids and does not look at the names when the question carries an id (`authority.rs:179-186`). A registration has no row, so the question is the typed name with the typed id: `RepositoryIdentity::registered(&parsed.full_name, parsed.github_repository_id)` in the API (`repositories.rs:504`) and `registered(name, *github_repository)` in the worker (`repository_changes.rs:578-583`). Ran (scratch probe in the domain test): with the listing `{name: acme/old-name, id: 5000}`, `covers_repository(registered("victim/secrets", 5000))` is **true**. `register_repository` needs only `operator` (`policies/approval.yaml:241`). The credential for a repository comes from the static installation list **by name** (`external.rs:268-290`, as REG-3 recorded).
- **Scenario.** An operator is narrowed to the repository `acme/a` (GitHub id 123), which is not registered yet, in an installation that also holds `acme/b`. They register id 123 under the name `acme/b`. Before RR-28, an entry by name `acme/a` could register any id under `acme/a`; now an entry by id registers id 123 under any name. The row binds webhooks of `acme/a` and acts on `acme/b`; the person is covered by the entry for every later act on that row (attest, disable, submit jobs, read). Contained today by three things: another operator or approver must still enable it (an approver reads the name in `show`), the intake stage re-reads GitHub for `acme/b` and judges the requester **by name** against the recorded name `acme/a` (here the by-name fallback of RH-3 happens to refuse), and the id can be registered only once. The refusal reply on a label event is not contained: the worker answers on the registered name (REG-3, scenario 3).
- **Fix recommendation.** When a listing has both a name and an id, require both for a registration (the typed name equals the recorded name without case and the ids are equal), because a registration is the one act that has no row to compare. The durable fix is REG-3's: register by asking GitHub for the repository id and storing GitHub's name and default branch, not the typed ones.
- **Why the tests miss it.** `an_operator_narrowed_by_the_github_id_follows_the_repository_through_a_rename_and_not_to_a_new_one_under_the_old_name` (`apps/api/tests/repositories.rs:1885-1987`) registers a **different id** under the old name and sees 403. It never registers the **listed id** under another name. The domain test asserts that the entry covers `registered("elsewhere/old-name", 5000)` as a feature (`crates/domain/tests/policy/authority.rs:1353-1364`), and the doc comment says "the names are not looked at" (`crates/domain/src/policy/authority.rs:172-176`).

### RH-3. The design approver is judged by name only; the ADR's "second, conjunctive check" is false for the design gate (MINOR)

- **Evidence.** The ADR says the stages "are a second, conjunctive check and not the first" because "a job or a decision reaches a stage only through one of the gates that asked with the id" (`docs/adr/0016-...md:261`). That holds for the requester: the webhook asks with the id first (`webhook.rs:199-207`). It does not hold for the **design approval**, which is a label applied on GitHub by a person. The webhook does not look at it (`grep -i 'design\|approved' apps/api/src/webhook.rs` finds nothing), `design_gate.rs` in the composition crate holds no allowlist, and the stage judges the applier with `authorize_designation(... judging.repository ...)` (`design.rs:267`), a plain name, which becomes `RepositoryIdentity::by_name_only` (`authority.rs:1066`): an entry with an id then "means the name recorded next to it". Ran (scratch probe): for the entry `{acme/old-name, 5000}` and a **new repository with id 9000 registered as `acme/old-name`**, the first layer says `covered=false` and the stage layer says `covered=true`. At the apply-time re-check of the worker the dependency decisions and the stage decisions (`unblock`, `approve_project_build_code`, `ack_translation_warning`) are also judged by name (`dependency_decisions.rs:547`, `stage_decisions.rs:641-643`); the API in front of them asks with the id, so for those two the stage is conjunctive. ### RH-4. Exactly once rests on a read followed by a write that can be passed (MINOR)

- **Evidence.**
  - `apply_in` reads `find_audit(result_id)` first (`repository_changes.rs:539`), then the principal, the repository and the allowlist, then changes the row (`:607-640`), then writes the result. Between the first read and the write there is no lock but the one the `UPDATE` takes, and the `UPDATE` is guarded by the version that this transaction **read after** the `find_audit`.
  - The module says "two workers that race write one result: the second one's transaction fails on the id" (`:34-39`). It does not fail. `record` runs `INSERT ... ON CONFLICT (tenant_id, event_id) DO NOTHING`, reads the stored row and returns it when the content is equal (`crates/storage/src/pg/audit.rs:167-203`); the result event is deterministic from the request, so it is equal. Ran: two transactions with the same event id, the second answers `INSERT 0 0`, no error, and the stored row is read back (`rh_result_twice`).
  - The remaining guard is the version. It stops the second worker only if the first worker's change is the last change of the row. If the first worker commits, an operator disables the repository, and then the second worker reads the row (the window is the few statements between its `find_audit` and its `get_repository`), the second worker's version is current and the same request applies again: an `enable` re-enables a repository that was just disabled.
  - The result id is `HMAC(current key, context || request id)` (`decision_signing.rs:824-831`) while a word verifies under the current and the previous key (`:622-632`). After a rotation `find_audit(result_id)` can no longer see any earlier result. The remaining guard is the scan of the log, which reads at most `PAGES_PER_PASS x PAGE` = 20 x 500 = 10,000 records before it applies what is still pending, and returns true even when the log is longer (`repository_changes.rs:92`, `:371-420`, `pass` at `:345-360`). A request whose result lies beyond the 10,000th record of a fresh worker's first pass is pending when it is settled, and after a rotation is applied again.
  - `change_status` in the API computes the result id with the current key too (`repositories.rs:653`). After a rotation every request that was applied before it reads `requested` for good, and the CLI's `repository change REQUEST` says the worker has not applied it.
- **Scenario.** Two workers (the hook allows several processes). Worker 1 applies `enable` for X and commits. The operator disables X. Worker 2, which had read "no result" before worker 1 committed, reads X now, finds the commit still attested and the version current, enables X, and finds the result row already there, which is not an error. X is enabled. The window is milliseconds and needs two workers and an operator in it: improbable, and it is the incident-response case again. The rotation variant needs a rotation, a restart and a request at the page boundary: improbable too. The status defect after a rotation is certain.
- **Fix recommendation.** Take the row first: `SELECT ... FOR UPDATE` on the repository, then `find_audit(result_id)`, in the same transaction, so the second worker sees the first one's result. Or insert the result first and treat `INSERT 0 0` as "done by someone else" and stop before the change. Check the result ids under **every** key in the rotation set (`current` and `previous`), in the step and in `change_status`, and write under the current one. Read the log to its end before the first application (loop until a short page), or apply only after the cursor has reached the end.
- **Why the tests miss it.** The exactly-once test is sequential and has one key. The `Rig` has no second worker that runs concurrently with an intervening change, no rotation and a log far shorter than 10,000 records.

### RH-5. The API login can write `repository.disabled` rows for any actor, and unsigned requests the status route believes (MINOR)

- **Evidence.** `audit_events_api_actions` limits the **action**, not the actor (`002700` up.sql:52-70; the message says "this action or this actor" but nothing tests the actor, and `2026-10-29-002100` says so on purpose). `repository.disabled` is the one action it may write for a repository, **and** the action the worker uses for its own effect record, with the system as actor (`repository_changes.rs:740-760`). Ran, as the real API login: an audit row with actor type `system`, actor `worker.repository`, action `repository.disabled` and the subject `request=<id> repository <id> disabled` is accepted; so is the same row as a person; so is a `repository.change_requested` row with a subject that has a bad word. `change_status` parses the subject and does not verify the word (`repositories.rs:648-693`), so a forged request reads `requested` forever.
- **Scenario.** A holder of the credential switches a repository off with a raw `UPDATE` (allowed, RH-10), which leaves no record, and writes a `repository.disabled` row as the system whose subject names a real, innocent `attest` request, so that an investigator reads "the table switched X off because that person attested the map again". The attacker can already disable; what they gain is a false story, and an innocent person in it.
- **Fix recommendation.** Give the worker's effect record an action of its own (`repository.disabled_by_attestation`) and keep `repository.disabled` for the API; add to the audit trigger that the API login may write `repository.*` only with a **person** as the actor (the webhook platform events that the 2100 comment mentions are not `repository.*`). Have `change_status` verify the word, or say in its answer that the request is unverified. Correct the trigger message.
- **Why the tests miss it.** `api_privileges.sql` and `repository_map.sql` section 12 check the list of **actions** both ways (`repository.change_applied`, `.registered`, `.map_attested`, `.enabled` refused) and write every row with `actor_type = 'human'` (`dbtest.api_audit`). Nobody tries the system as the actor on the allowed actions.

### RH-6. `single_maintainer` is chosen by the role it constrains (MINOR)

- **Evidence.** `register_repository` needs `operator` (`policies/approval.yaml:241`); the flag is a field of the registration body (`RegisterBody.single_maintainer`) and of the CLI (`commands.rs:946-995`, `--single-maintainer`); the worker applies it as registered (`repository_changes.rs:604-617`); the strict rule then applies to `enable_repository`, an `approver` act. A person who holds `operator` and `approver` registers with `--single-maintainer`, attests, enables: three commands, which is what REG-6 meant to stop. The audit record of the registration says `single_maintainer=true` and `show` prints "Rule: single maintainer"; nobody is told. T-38 says "This protects against a person who holds both designations" (`threat-model.md:539`). It protects against one who did not choose the exception.
- **Scenario.** As above. A team repository, one careless or hostile person with both designations, one flag.
- **Fix recommendation.** Make the exception need more than the role it exempts: a designation the person does not use for the other acts (`org_admin`), a second person's signed countersign, or a list in the protected configuration of the GitHub ids that may be single-maintainer, checked by the worker when it applies the registration. Or accept it as the project owner's decision and rewrite T-38:539 to say who is protected from what.
- **Why the tests miss it.** They prove that the flag is chosen at registration and cannot be changed afterwards (`repository_map.sql` 11b; the CLI test at `api_calls.rs:1070-1139`). They do not ask who may choose it.

### RH-7. Enabling an enabled repository is accepted and recorded as the second person's act (MINOR)

- **Evidence.** The API's pre-check refuses an attestor and a changed commit and does not refuse an enabled repository (`repositories.rs:605-612`). The store's `UPDATE` has no `NOT enabled` condition (`jobs.rs:1122-1126`). The table keeps the first record when the repository stays enabled (`002600` up.sql:122-127). Ran, with the statement of `enable_repository` as the worker login, for a repository enabled by B and asked now by C: `UPDATE 1`, version 3 -> 4, and the table still records B. The worker then writes `repository.enabled ... enabled by C` (`repository_changes.rs:688-736`).
- **Scenario.** Two approvers both enable. The audit log, the evidence for separation of duties, names C; the table (`enabled_for`, `show`) names B. A later reader trusts one of them. The version also moves, which makes the worker's own optimistic writes for the same repository retry (RH-10).
- **Fix recommendation.** Refuse `enable` of an enabled repository: a `409 already_enabled` at the API, a recorded refusal `already_enabled` at the worker, and `AND NOT enabled` in the statement.
- **Why the tests miss it.** `repository_map.sql` section 10 shows that the record does not move while the repository stays enabled, as a feature, and the API test enables once.

### RH-8. An empty enabler is not judged (NOTE)

The CHECK and the trigger judge the pair only when both are named (`002600` up.sql:67-72, 141-145). The worker group holds a table-level `INSERT` on `repositories` (`privileges.sql:41`), so a holder of that credential runs one `INSERT` with `enabled = true`, a map commit, an active attestor, `single_maintainer = false` and no enabler: accepted, `enabled_by_principal_id` empty, enabled for the map commit (run). T-38:539 says "the table refuses the pair for every role"; it refuses a **named** pair. The worker credential can already write principals, tokens and approvals (`2026-10-28-002000`), so this is inside what it holds; it matters only because the sentence is stronger than the table. If the project wants it, make the table refuse `enabled` with an empty enabler for the worker group.

### RH-9. Migration facts (MINOR)

### RH-10. A holder of the API credentials can switch off every repository of every tenant and starve every re-enable (NOTE)

Naming a tenant by hand is the model (ADR 0012), so a login that may switch a repository off may do it in every tenant (run: with tenant 2 named, `UPDATE 1`). Switching off an already-off repository is allowed and raises the version (`repository_map.sql` section 12, "the sibling"); the worker's `attest`, `enable` and the guard `version = $3` then see a moved row, answer `Conflict`, the step says `Later`, and after 20 passes it records `not_settled` (read). A tight loop of version bumps therefore turns re-enable requests into refusals. "Narrowing is safe" is true for integrity and not for availability, and the migration headers say the first half. A raw `UPDATE` writes no audit row, so the only trace is a version number that has no record behind it. Suggestions: a periodic reconciliation of `repositories.version` against the count of records for the repository; or a function owned by the owner that does the disable and writes its record in one call, with the table `UPDATE` revoked from the API login. Neither stops a holder of the credential from switching off; both make it visible.

### RH-12. The worker does not re-validate the shape the API validated (NOTE)
