# Security review of the design gate at intake

- Reviewer: an independent security reviewer (Claude Sonnet 5.5), working alone from the repository. I wrote none of the code under review and changed none of it. My only addition is this document. I wrote no test target.
- Date: 2026-11-02. Reviewed commit: `b33d96e` (`feat/slice-0-foundation`, the merge of the design gate). The change is `git diff c5b8738...worktree-agent-a03d5c5323000d1b5`.
- Question: can an issue that a person would call "on the design track" start work without a design that a person holding the `approver` designation approved; can a label that is not `design: approved`, or an approval that was not made by an approver, be accepted; can the refusal be passed by an override, an unblock, a rework or a retry; and can untrusted text reach a comment, an audit record or a log.
- Environment: reading only. `git show`, `git diff`, `grep`, file reads. I did not run `cargo`, the test suites, PostgreSQL or Docker (a long test run was using the machine, and I was told not to). **Every statement below is from reading the code, not from running it.** Where I rely on GitHub behaviour that nobody in this repository has observed, I say "unverified".
- Evidence: none by test. Each finding names the file and line, the scenario, why the existing tests do not catch it, and a fix.

## 1. Verdict

**PASS WITH CONDITIONS**, for use by the builders and one tenant. **I found no BLOCKER.**

The core of the gate is sound. The labels are read from the code host at intake and not from the webhook. The approving label is compared byte for byte. Anything that starts with `design:` in any letter case puts the issue on the track, and a look-alike of the approving label puts it on the track without approving it. The applier is found by numeric id on a fresh allowlist, the entry may not be narrowed away from the repository, and a label with no findable applier is a refusal. A refusal is blocked as a policy violation, and I traced the override path to the end: the block is in the engine's own list and no override, unblock, rework or approval passes it (section 4, question 6). A broken policy file refuses every issue. The refusal comment holds no text of the issue. I reasoned through the twelve spellings of the tests and about a dozen more by reading the code, and none of them gave an approval of the approving label.

**Why not PASS.** Three things, all MAJOR.

1. **DG-1.** The adapter that tells the gate who applied the label reads at most 1000 issue events, oldest first, and when the list is cut it still answers from the newest `labeled` event it found. If the real, later application sits beyond the cut, the gate is shown an older application by an approver. A person without the `approver` designation can therefore have their own application counted as an approver's, on an issue whose label was approved once and then reopened, after enough events were added to the issue. The test double cannot model this.
2. **DG-2.** An issue is on the track only while it carries a `design:` label, and the Action explicitly allows taking one away. A requester (who holds triage rights, or could not apply `factory`) removes the labels and applies `factory`. The documents say "the label on the issue is the one way through" and the policy says the person who asks for work must not approve the design. Neither is true of a requester who strips the label.
3. **DG-3.** A job started through `POST /v1/jobs` or `factory-cli submit` carries text that the caller typed and a `source_ref` that names any issue of the repository. The gate judges the issue the `source_ref` names. A requester who copies the text of an unapproved design into a job that points at an unrelated, labelled issue gets the work done.

DG-2 and DG-3 are bypasses by a person who is already on the requester allowlist. If the architect accepts that a requester is trusted not to do this, they become NOTEs, and then the documents (guide, ADR, threat model T-23, the comment in `policies/security.yaml`) must say so instead of "the one way through". DG-1 is the only one that lets a person who holds no designation reach further than their designation.

**Conditions.** Close DG-1 before the first run against a real GitHub. Decide DG-2 and DG-3: fix, or write them down as residual risk with an owner. The six MINOR findings can follow. The gate has been run against fakes only, and the fake cannot show DG-1, DG-4, DG-5 or DG-6 (section 6).

**What the verdict does not cover.** Everything that needs the real GitHub, a running worker with a database and an App, and the Action running on GitHub (section 6).

## 2. Severity scale

BLOCKER: do not use against a real GitHub, or by anyone but the builders, until closed. MAJOR: a control the documents promise is weaker than promised, or a party can reach further than its designation, and the fix is cheap before wider use. MINOR: defence in depth, a wrong reason, an inaccurate claim, observability. NOTE: worth knowing, no action needed now. There is no BLOCKER.

### DG-1. A cut event list still answers from an older application (MAJOR)

- **Evidence.** `label_application` reads the events with `get_pages` (`crates/github/src/issues.rs:201-204`). The reader asks for 100 per page and stops after 10 pages (`crates/github/src/client.rs:27-39`, `237-276`), then returns `truncated: true`. The code takes the last `labeled` event for the label in what it got (`issues.rs:206-208`) and returns it. Only the case "no event found and the list was cut" is an error (`issues.rs:217`); "event found and the list was cut" falls into the first arm (`issues.rs:210-213`) and returns the actor. The list is oldest first (unverified, see DG-11), so the cut drops the newest events, which are the ones that matter. The design gate takes the actor from this call (`handler.rs:991-1000`), and so does the check of the `factory` label (`handler.rs:184`).
- **Scenario.** A design is approved. An approver applies `design: approved` (event 25). Later the design is reopened and the label comes off; the state moves to `design: in progress` and back to review. A person with triage rights who holds no designation wants the issue to start. They add and remove a label that nobody watches until the issue has more than 1000 events (about 500 add-and-remove pairs, a few hours at the limits GitHub puts on writes, unverified), then apply `design: approved` as the last event. The label is on the issue, it is the one design label, the adapter reads events 1 to 1000, finds the approver's application at event 25, and reports the approver. The gate passes. The same happens with no malice on a long thread where a non-approver re-applies the label late. The Action would revert an illegal move if it is installed and runs in time, but it is "a consistency tool, not a security control" (ADR 0016, line 68).
- **The reverse case.** An honest approval applied after event 1000, with no earlier application, is an `Unavailable` error and never passes: the issue is stuck, and the comment says nothing, because the attempt fails and is retried (`handler.rs:995-996`).
- **Why the tests miss it.** The test double stores one actor for each (issue, label) (`crates/testkit/src/githost.rs:1046-1062`); it has no events, no order and no pages. The adapter's own tests re-apply a label by another person (`crates/github/tests/security_review/main.rs:420-482`) but never past the page cap; a search for `truncated` in `crates/github/tests` finds nothing for this method. `crates/github/tests/mutations/run_mutations.py` has no entry for `issues.rs`.
- **Fix.** When `events.truncated` is true, return `Unavailable` in both arms, whatever was found. Better, make the call able to see the end of the list: follow `rel="last"` or raise the cap for this call and fail if it is still cut. Add a test that builds 1001 events with an approver's application first and another person's last, and a mutation of `issues.rs` for the `truncated` arm and for `.rev()`.

### DG-2. Leaving the track needs only triage rights (MAJOR; NOTE if the architect accepts it)

- **Evidence.** The rule is "any label that starts with `design:`" (`crates/domain/src/policy/issue_workflow.rs:486-491`, `495-519`); with none, the result is `NotOnTrack` and nothing else is read (`intake/design.rs:177`). The engine reads `labeled` events only (`issues.rs:206-208`). The Action says "taking a design label away leaves the track, which is allowed" (`scripts/lib/issue_workflow.py:360`). ADR 0016 line 78 says a small change "has no `design:` label". The comment in `issue_workflow.rs:696-698` says "the person who asks for work must not approve the design", the guide says "the label on the issue is the one way through", and `policies/security.yaml:1219-1224` says "the label is the one way through".
- **Scenario.** An issue made from the "new solution" form carries `design: proposed`, applied by the template. A requester with triage rights (needed to apply `factory`) removes it, then applies `factory`. The engine sees no design label, the job starts, and the timeline shows an `unlabeled` event that the engine never reads. The same result without removing anything: the requester opens the issue by API or CLI without the form, so it never had the label.
- **Why the tests miss it.** The tests start from a label list; `an_issue_with_no_design_label_is_accepted_as_before` (`crates/workflow/tests/intake_repo/design.rs:207`) pins exactly this outcome.
- **Fix.** Make the track sticky: if the timeline holds any `labeled` event of a label that starts with `design:` (even one that was removed), the issue is on the track and needs `design: approved` applied by an approver. The way out of a design that was dropped is then one approver action. A cheaper variant: an `unlabeled` event of a design label whose actor does not hold the approver designation puts the issue on the track. Either needs the full event list, so DG-1 must be closed first. If neither is wanted, write it in T-23 and the guide as residual risk, and remove "the one way through".

### DG-3. API and CLI jobs: the text is not the issue (MAJOR; NOTE if the architect accepts it)

- **Evidence.** `POST /v1/jobs` requires a `source_ref` that parses as `owner/name#number` in the registered repository (`apps/api/src/jobs.rs:152-162`, `186-194`) and stores the caller's text as revision 1 (`jobs.rs:230-239`). `factory-cli submit` requires `--source-ref` (`apps/cli/src/commands.rs:249-252`). At intake `latest()` returns the stored text and the issue from `source_ref` (`crates/composition/src/seams.rs`, `latest`); only a job with no stored request fetches the issue's text (`handler.rs:392-425`, `1104-1170`, the webhook path). `judge_design` fetches the issue, including its title and body (`handler.rs:980-989`), and compares nothing with the stored text.
- **Scenario.** A requester files a trivial issue 99 with no design label and applies `factory` to it. Then `factory-cli submit --source-ref owner/repo#99 --text-file proposal.md`, where `proposal.md` is the text of issue 10, a design-track issue whose design is not approved. Intake authorizes the label on 99, judges 99 (not on the track) and classifies the text of 10. The factory builds the unapproved design, and no record connects the job to issue 10. A `source_ref` that names a pull request does not work: see question 4.
- **Documents.** "A job with no issue is outside the design track" is moot: there is no job with no issue. Both entry points refuse a missing `source_ref` (`jobs.rs:155-162`, `commands.rs:252`), and a stored request with none is `NotFound` and then an internal error (`handler.rs:392-405`). What the documents do not say is that the text and the issue are tied. ADR 0016 says only that the engine "must check the design state itself when it accepts an issue" (line 68). FR-001 says a job is for one issue.
- **Why the tests miss it.** Every test in `design.rs` stores the same text and issue by construction (`rig.job(USUAL_REQUEST)`); none submits text that differs from the issue's.
- **Fix.** The cheapest: in `judge_design`, where the live issue is already in hand, compare the text it would give (title, blank line, body, through the redactor as `first_request` does) with the stored text, and refuse or ask a person when they differ; or make API jobs take their text from the issue like webhook jobs do and keep the caller's words as an added note. Record the comparison in the audit line.

### DG-4. Format characters and look-alikes hide a label from the track (MINOR)

- **Evidence.** The head test trims leading white space and control characters only and then compares seven bytes without case (`issue_workflow.rs:486-491`). Zero-width and bidirectional characters, the soft hyphen and the byte order mark are category Cf, not white space and not control, so they are not trimmed. A full-width colon, a Cyrillic or Greek letter and a Unicode letter that case-folds to ASCII are not equal to the ASCII key. The same repository removes exactly these characters from issue text (`crates/github/src/issues.rs:43-61`) and does not apply that to label names. There is no normalization of any kind on the label names; the approving label is compared with `==` (`issue_workflow.rs:503-508`), which is right for approval and wrong for track detection. `unicode-normalization` is already a dependency of `factory-ports` (`crates/ports/Cargo.toml:35`).
- **Scenario.** A label named with a leading zero-width space and then `design: proposed` looks like a design label on GitHub and is `NotOnTrack` for the engine. By itself this gives a requester nothing that removing the label does not (DG-2), and creating the label needs write rights. It matters because the track is meant to be what people see, and because the one test that touches it asserts the opposite of safe: `a_look_alike_beside_a_real_design_label_does_not_hide_it` lists `"\u{200b}design: approved"` as "just another label" (`tests/intake_repo/design.rs:455-480`). That test shows the label beside a real one, never alone.
- **Why the tests miss it.** The twelve spellings of `tests/intake_repo/design.rs:405-453` all start with the exact seven characters. None puts a format character or a non-ASCII letter inside them.
- **Fix.** For track detection (not for approval), strip category Cf, Cc and Zs from the head, apply NFKC, case-fold, and compare; or treat any label with a non-ASCII character in its first ten characters as on the track. Keep the approving label exact. Add the cases as a table.

### DG-5. The applier is always a "User" (MINOR)

- **Evidence.** The adapter keeps the numeric id and drops the account type and the `[bot]` suffix (`crates/github/src/parse.rs:23-35`). The gate builds the actor with `kind: ActorKind::User` (`crates/workflow/src/stages/intake/authorize.rs:136-143`). `AuthorityPolicy::designations` rejects a non-user (`crates/domain/src/policy/authority.rs:953-955`), which therefore cannot happen on this path, and `DenialReason::NotHuman` is unreachable. The policy says `bots_may_be_listed: false` and gives the approver role `must_be_human_user: true` (`policies/approval.yaml:129`, `152`).
- **Scenario.** `github-actions[bot]` and the factory's own App are not on the allowlist, so a label they apply is refused for `NotAllowed`. That is the safe default. If an operator lists a bot's numeric id by mistake (a machine account of type Bot, or the App), the gate approves what it applies. Nothing in the code stops the entry or the use.
- **Why the tests miss it.** The test double has no account type (`GithubActor` is id and login only), so no test can show a bot.
- **Fix.** Add the account type to `GithubActor` from the event's `actor.type` and pass `ActorKind::Bot` when it is `Bot`. The same change gives the `factory` check its human test.

### DG-6. A partial answer reads as "no labels" (MINOR)

- **Evidence.** `fetch_issue` builds the label list with `as_array().into_iter().flatten().filter_map(...)` (`crates/github/src/issues.rs:118-123`). A body with no `labels` member, a `null`, or elements that are strings (GitHub's own description of the field allows strings or objects, unverified for this call) gives an empty list. An empty list is `NotOnTrack` and the gate passes. `label_application` reads the same member the same way (`issues.rs:193-197`) but there an empty list means "label gone", a refusal. The title and body also default to empty (`issues.rs:115-116`).
- **Scenario.** A proxy, a cache, a changed response format or a partial body that still parses. The gate, which "fails closed" everywhere else, turns off.
- **Why the tests miss it.** The fakes return typed values; no test feeds `fetch_issue` a body without `labels`.
- **Fix.** Parse strictly: `labels` must be an array whose elements are objects with a string `name`, or the call fails with `Unavailable`.

### DG-7. A label name can forge a field of the audit line (MINOR)

- **Evidence.** `audit_reason` writes the labels between brackets, joined with `, `, and then more fields after `; ` (`intake/design.rs:359-365`). `printable_label` keeps every printable ASCII character, including `;`, `[`, `]` and `,`, and cuts at 60 characters (`issue_workflow.rs:415-425`). GitHub allows 50. A name such as `design:]; approved label applied by user id 77;` (47 characters) starts with `design:`, is on the track and is written into the line, which then reads as if the approved label was applied by user id 77 before the real field follows. The doc comment says a hostile name "cannot change the line it is written in"; it cannot add a line break, which is all it can claim. The gate report has the same pattern with `|` (`intake/design.rs:466`). The reason is cut at 1000 bytes (`crates/workflow/src/engine/record.rs:498-504`) and is not passed through the redactor (`record.rs:489-515`), so a secret-shaped label name is stored.
- **Scenario.** A person who can create labels makes an investigation read a forged approver id. The record still says "refused", so this is a misleading line and not a bypass.
- **Why the tests miss it.** `a_look_alike_of_the_approved_label_cannot_count_as_approved` checks that no control character reaches the audit (`tests/intake_repo/design.rs:430-447`), and no test looks for delimiters.
- **Fix.** Write the labels as a JSON array string (`serde_json::to_string`) so the delimiters are quoted, and pass the reason through the redactor of the job. State what `printable_label` guarantees: no control characters.

### DG-8. The design is checked once (MINOR)

- **Evidence.** No code outside the intake stage reads a design label (a search for `DesignGate`, `design: approved` and `DESIGN_NOT_APPROVED` finds only the intake module, the composition root, the policy types and tests). The delivery stage and the approval stage do not look at the issue. The job runs the whole pipeline (`crates/workflow/src/engine/config.rs:67-81`).
- **Scenario.** An approver applies the label, the job starts, the approver notices a flaw and reopens the design (`design: in progress`; the Action removes `approved`). The job goes on to a draft pull request. The output is a draft, a person merges (`merge_pr` is off), so the cost is a wasted run and a draft for a design its approver reopened. The approver's act of revoking does not revoke.
- **Fix.** Read the labels again before delivery opens the pull request and refuse if the issue is on the track without an approved design, or say plainly in the guide that approval is a one-time check at intake.

### DG-9. The refusal reply (MINOR)

- **Evidence.**
  - *Volume.* The key is `design-gate-{stage_run}` (`handler.rs:1027`). A requester who removes and applies `factory` again makes a new job for each application, because each `labeled` event has a new `updated_at` in the semantic key (`crates/github/src/webhook.rs:298-318`) and the webhook path has no cap by issue or by requester (`apps/api/src/webhook.rs:194-260`). The one bound I found is 120 deliveries a minute for an installation (`apps/api/src/config.rs:138-140`). ADR 0016 names it (architect question 6).
  - *De-duplication.* `post_comment` looks for its marker in the first 1000 comments and does not read `truncated` (`crates/github/src/changes.rs:394-399`). On a longer thread, each attempt posts again.
  - *Token.* The reply mints a token for a random job id and revokes it unless the result is `Later` (`crates/composition/src/design_gate.rs:166-193`). A comment endpoint that answers `Unavailable` or rate limits leaves up to three narrowed `issues: write` tokens for the stage run until GitHub expires them.
  - *Order.* The comment is posted before the audit record is written (`handler.rs:501-526`). If the comment returns `Later`, the attempt fails with a tool error, and after the third the stage run fails: the job is FAILED and not BLOCKED, with no `design_not_approved` code and no design audit line. Fail closed holds; the record is lost.
- **Why the tests miss it.** `a_comment_that_cannot_be_posted_now_fails_the_attempt_and_is_tried_again` (`tests/intake_repo/design.rs:574`) checks the retry and not the record or the token.
- **Fix.** Write the audit record first; cap refusals by issue (for example one reply a day for the same issue and reason); read `truncated` in `post_comment`; revoke on every outcome.

### DG-10. Policy shape (NOTE)

- The block is in `policies/security.yaml:1225-1228` and is passed to the engine at `crates/composition/src/pipeline.rs:827`, but it is not in the engine's own floor, which holds one block (`crates/workflow/src/engine/config.rs:136-139`). A composition that does not call `with_non_overridable_blocks` makes it overridable. A test pins the file (`tests/intake_repo/design.rs:746`) and the real worker passes it, so this is a hardening, not a hole.
- `design_track_requires` may name any design state; `problems()` checks only that the state exists (`issue_workflow.rs:678-684`). Set to `proposed`, the weakest label would approve. A review of the policy pull request is the guard.
- One allowlist entry may hold `requester` and `approver`. `separation_of_duties.approver_may_equal_requester_when_low_risk: true` (`policies/approval.yaml`) allows it for single-maintainer repositories. The comment in `issue_workflow.rs:696-698` is about the designation named, not the person, and should say so.
- If the deny-only permission condition of the authority policy were ever turned on, the intake passes no permission (`authorize.rs:141`), so it would deny every requester and every approver. This fails closed and is pre-existing.

### DG-11. What nobody observed (NOTE)

The gate rests on GitHub behaviours that the repository's own notes say are unobserved. Each is a refusal or an error if it is wrong, except where I say so. (1) The events list is oldest first (the Rust code uses `.rev()`, the Python tool the same assumption). If it were newest first, the code would credit the oldest application: a bypass. (2) The label name inside an old `labeled` event is the name at the time of the event. If GitHub shows the current name, a person with write rights who renames another state label to `design: approved` turns earlier applications by approvers of that label into approvals: a bypass. (3) Applying `DESIGN: APPROVED` through the API resolves to the one existing label and shows its canonical name; if the events show the name as typed, the gate refuses (safe). (4) The actor of an event by a deleted account is `ghost` with a fixed id, which is not on the allowlist, so a deleted approver's approval is void (safe, and surprising). (5) A label deleted and created again drops or keeps its old events; either is safe. (6) A user-to-server token of an app acting for an approver is shown as the approver; the gate cannot tell.

### DG-12. The Action and the engine (NOTE)

(1) The Action accepts `design: approved` from anybody with triage rights if a design document exists; the engine accepts it only from an approver. The engine is stricter, which is right. (2) The engine accepts what the Action would revert for as long as the Action takes, or for ever if it is off: an approver applies `approved` on an issue with no design label or with a move the Action calls illegal (`issue_workflow.py:369-376`), and the engine reads the label before the Action removes it. The engine never checks that a design document exists, so with no Action nothing does. That is documented ("holds even if the Action is off") and is the approver's responsibility. (3) The Action does not remove `Design: x` or `design:x`, so a look-alike left on the issue refuses it until a person removes it by hand; this is safe and a nuisance. (4) The Action's comment still says "Until the factory itself checks this, a person has to watch for it" (`issue_workflow.py:334-336`), which is no longer true. I found no interleaving where the Action adds a `design:` label (its only `add_label` is for `factory:` labels, `issue_workflow.py:353`), so the Action cannot make an approver of itself. A `design: approved` label that the Action removed and that a person puts back is a new application, by the person.

## 4. Answers to the nine questions

**1. Bypass by label spelling.** *No bypass of the approving label; one gap in the track test (DG-4).*

- Case: the track test ignores ASCII case (`issue_workflow.rs:489-490`), the approving test is exact (`:503-508`). `Design: approved` is on the track and not approved. Covered by `tests/intake_repo/design.rs:405-453` and the unit test `issue_workflow.rs:923-945`.
- A missing space, a doubled space, a trailing space and a leading space or tab: on the track, not approved (same tests). A trailing newline or NUL: same.
- A zero-width character, a soft hyphen or a bidirectional mark after the first seven characters (`design: appro\u{200b}ved`) or a Cyrillic letter there: on the track, not approved (`issue_workflow.rs:936-937`). The same characters before or inside `design:`, or a full-width colon: **not on the track** (DG-4).
- A different colour or description: the code reads names only. GitHub allows one label per name in a repository, so a second label with the same name and another colour cannot exist (unverified).
- A label on a pull request: `fetch_issue` refuses any item with a `pull_request` member (`issues.rs:110-112`), the gate fails with a tool error and the attempt is retried until the stage run fails. This is a refusal, not a pass. The adapter's `label_application` has no such check (`issues.rs:183-199`), so the requester check passes first and the gate then fails; the cost is three attempts and up to about 35 requests each. The webhook cannot start a job from a pull request: it needs the `issues` event (`crates/github/src/webhook.rs:343-344`), and a pull request sends `pull_request` events.
- Normalization: none. Byte-exact for approval, ASCII fold for the prefix, no NFC, no NFKC, no stripping of category Cf.
- The two tests work on the same raw strings: `classify` filters `fetched.labels` once and tests the survivors with `==` (`issue_workflow.rs:496-508`); only the head test trims, and it trims a copy.

**2. Bypass by who applied it.** *DG-1 and DG-5; every other case is a refusal.*

- An approver applies: accepted if the entry is on the allowlist now, not expired, not narrowed away, and holds `approver` (`authorize.rs:128-143`, `authority.rs:953-971`).
- A non-approver removes and re-applies: a new `labeled` event with that actor, so the latest event is theirs and the gate refuses (`issues.rs:206-208`). Correct while the list is whole (DG-1).
- `github-actions[bot]` or the App: refused because the id is not on the allowlist, not because it is a bot (DG-5). The App writes `factory:` labels only; the type system keeps it from writing a `design:` label (`issue_workflow.rs:20-23`).
- Renamed approver: the id is stable, so the approval stands. Deleted approver: shown as `ghost` (`parse.rs:25-29`), whose id is not on the allowlist, so refused; an event with a null actor is `Ok(None)`, "nobody is credited", refused (`issues.rs:210-215`).
- Removed from the allowlist after applying: the allowlist is read now for each attempt (`seams.rs:123-132`), so refused. Tested (`tests/intake_repo/design.rs:291`).
- Entry narrowed to other repositories: refused; case-insensitive compare of `owner/name` (`authority.rs:162-168`). Tested (`tests/intake_repo/design.rs:264`).
- Two applications: the later one counts, and the list order is assumed (DG-11).
- Which application and how many events: the latest `labeled` event in the first 1000. Hundreds of events are fine; more than 1000 is DG-1.
- Adapter cannot tell: an `Err` fails the attempt (`handler.rs:995-996`), `Ok(None)` is a refusal (`intake/design.rs:200-203`). No case I found turns an error into a pass, except the cut list in DG-1.

**3. Time of check and time of use.** *DG-8.*

- Between the gate and later stages: nothing re-checks. A label removed or a second design label added after intake changes nothing for a job already started. Bounded by the draft pull request and the human merge. Finding DG-8, MINOR.
- Within the gate: it reads the issue (`fetch_issue`) and then asks for the applier (`label_application`, which reads the issue again). A second design label added between the two reads is not seen; the window is one round trip, and the next intake sees it. Not worth a finding.
- Text edited between the authorization and the gate: the gate judges labels, not text, so an edit does not change its result. For a webhook job, `first_request` refuses text edited after the `factory` label (`handler.rs:1125-1133`, `LABEL_SKEW_SECONDS`). An edit after `design: approved` and before `factory` is not caught; the requester who applies `factory` is the one who reads the issue. The approval is not bound to the text or to the design document the issue names. NOTE.
- A stale approval is worth the MINOR in DG-8 and no more.

**4. Paths that never meet the gate.** *None skips the gate; DG-2 and DG-3 are about what the gate is shown.*

- `POST /v1/jobs` and `factory-cli submit`: a `source_ref` is required (`jobs.rs:155-162`; `commands.rs:249-252`). Without one: 400, and no job. With one for a different issue than the text: accepted (DG-3). For a pull request: accepted at submit, fails at intake (question 1).
- The webhook: `factory` on an issue by an allowlisted requester makes a job (`webhook.rs:194-260`); the text is fetched live and bound to the issue (`handler.rs:1104-1170`).
- Re-run, rework, retry, unblock: each runs `execute` again from the top and judges the labels again; there is no stored "already passed" (`handler.rs:392-535`). Rework has no route to or from intake (`crates/domain/src/machines/rework.rs:236-313`).
- A second job on the same issue: a new job, a new intake, a new judgement.
- A requester with a job whose text came from a design-track issue and carries no reference to it: yes (DG-3). The reference exists; it points elsewhere.
- Is "a job with no issue is outside the design track" acceptable under the documents? There is no such job, so the question does not arise. If one were made (a row written by hand), `latest()` is `NotFound` and `awaiting` is empty, so the stage fails with an internal error (`handler.rs:392-405`): it fails closed.
- Every job has `SLICE_ONE_SCOPE`, which starts at intake (`engine/config.rs:67`), set in both entry points (`jobs.rs:195`, `webhook.rs:236`).

- A partial answer: DG-6 (fail open) and DG-1 (cut list).

Only the policy file causes it, and that file is on the protected default branch of the factory's configuration (`design_gate.rs:60-80`). A requester cannot change it. The rate of GitHub calls (up to about 35 per intake attempt) is a minor lever for a requester against the App's rate limit; the one bound is 120 deliveries a minute.

**6. No way through.** *Held for the block; the claim "the one way through" is false (DG-2, DG-3).*

- The refusal sets `policy_violation` (`handler.rs:859`, `936`); `resolve` returns `Blocked(PolicyViolation)` first (`resolve.rs:101-103`); `blocks_of` lists every BLOCKED report, including `(intake-design-approved, design_not_approved)` (`gate.rs:759-785`); the override requires that none of the stored blocks is in the engine's list, and an empty list is refused (`decide.rs:432-437`). Approving the specification stage is another run, after intake. Rework has no route from or to intake (`rework.rs:236-313`). A new attempt runs the gate again.

**7. Output and injection.** *Held, with DG-7 and DG-9.*

It holds nothing from the issue. A test checks that no reply names a person or a list (`intake/design.rs:501-539`). It goes through the output hygiene (`changes.rs:385`). **8. The Action and the engine disagree.** *Four disagreements, no bypass (DG-12).* The engine reads who applied; the Action reads whether a document exists. The Action never adds a `design:` label, so it cannot produce an approval. The race window is the latency of the Action; with the Action off it is unbounded. The Action's `reconcile` reads all event pages (`gh api --paginate`) and the engine 10, which is DG-1.

## 5. What held

- The override cannot pass the block, and I looked at every path that could: the stored blocks include the design gate's block even though the run is blocked for a policy violation, and an empty list is refused.
- Intake always reads the labels itself, and a webhook payload is never an input of the gate (`handler.rs:969-1018`).
- A label with no applier is a refusal, and the applier is the actor of the latest event, not the sender of the webhook.
- The approving label is exact; the look-alikes of the approving label that start with `design:` approve nothing.
- The policy is strict and read on every attempt; an unreadable policy is a refusal of everything.
- Numeric ids, a fresh allowlist, the expiry and the repository narrowing are the same function as for requesters (`authorize.rs:101-168`), with a different designation.
- The comment holds no issue text, and a failure to post it does not change the refusal.
- No job lacks an issue reference; both entry points require one; all start at intake.
- A pull request cannot pass the gate, and the Action cannot add a `design:` label.
