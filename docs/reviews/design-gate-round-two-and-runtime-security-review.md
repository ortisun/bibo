The first review is [design-gate-security-review.md](design-gate-security-review.md); its DG-1 to DG-12 and its Fix status are the baseline.

## 1. Verdict

**PASS WITH CONDITIONS**, for use by the builders and one tenant. **I found no BLOCKER.**

The second round is better than the first. The five things I attacked hardest held: the text compared at intake is the string that is consumed (no gap, section 4 question 1); the re-check before the pull request has one path to the push and fails closed in every error path (question 2); a pasted marker or a cut page never counts as "already replied" (question 3); no caller can widen the intake token and a released token is replaced by an ordinary mint (question 4); a configuration value cannot make a link host outside the list appear in a comment, because the adapter filters it (question 5). The service images are what the documents say: both bases are pinned by digest, the user is numeric, the program is the one root-owned file, and I found no secret or personal path in the layers (question 6).

**Why not PASS.** One MAJOR and seven MINOR findings.

1. **DR-1 (MAJOR).** DG-3 ties the words of a job to the live issue, but the design approval is still tied to a label and not to the words. A requester or the issue's author can edit the body after an approver applied `design: approved` and before `factory` is applied, and the factory acts on the new words with the old approval. The threat model lists "an issue body edited after a maintainer authorized it" (T-23) and the approver's authorization is the one that is not covered.
2. **DR-3, DR-4, DR-5, DR-6** are controls that the documents describe more strongly than the code: the record "before" the reply is an in-memory note that the engine drops on a cancel, a lease loss or a crash; the explanation of a refusal can be silenced for a day by anyone who can fill one page of a thread; the new fsaudit option makes two credential patterns blind in every file that is not plain text or is larger than 4 MiB (I ran it); `sandbox.docker_config` names a Docker daemon through a context and so walks around the rule that the production profile does not reach a daemon over a network.
3. **DR-2, DR-7, DR-8** are smaller: the answers of people are appended to the text after the comparison; the image build context does not exclude most credential-looking names; and parts of the loopback judgments cannot fail.

**Conditions.** Decide DR-1 (fix it, or write down that an approval covers the design and not the words, with an owner) before the first run against a real GitHub. Fix DR-5 before anyone relies on the image audit for the two programs; the fix is one regular expression. Fix or reword DR-3 and DR-6 where the documents overstate them. The rest can follow. Everything ran against fakes and the Docker daemon of this host; nothing ran on the real GitHub.

**What the verdict does not cover.** Everything that needs the real GitHub (the `since` parameter, a page of 100 comments, the order and shape of events, whether a token request with only `issues: read` and `metadata: read` is accepted), a running worker with a database and an App against a job that is blocked, and the Rust test suites, which I did not run.

## 2. Severity scale

BLOCKER: do not use against a real GitHub, or by anyone but the builders, until closed. MAJOR: a control the documents promise is weaker than promised, or a party can reach further than its designation, and the fix is cheap before wider use. MINOR: defence in depth, a wrong reason, an inaccurate claim, observability. NOTE: worth knowing, no action needed now. There is no BLOCKER.

### DR-1. The approval is not bound to the words of the issue (MAJOR; NOTE if accepted)

- **Evidence.** At intake `DesignJudge::judge` fetches the issue once and compares the stored text with the title and body of that same answer (`crates/workflow/src/stages/intake/judge.rs:153-169`). The result can only refuse a job that the labels would let through (`design.rs:293-298`: `NotOnTrack` or `Approved` with `Different` becomes `TextNotTheIssue`). The approval itself is a label whose applier holds `approver` (`design.rs:265-291`); nothing in the decision relates it to the words: no hash of the body at approval time, no time of the last edit. The one place that looks at an edit time is `first_request` (`handler.rs:1262-1270`): it compares `fetched.updated_at` with the application of the **trigger** label (`application` comes from `authorize_label`, `handler.rs:1258`) plus 5 seconds (`handler.rs:88`), and it runs only for a job that has no stored text yet. The re-check before the pull request passes `stored_text: None` (`design_recheck.rs:124`). The threat model lists "an issue body edited after a maintainer authorized it" (T-23, attack line); the control in the code for it is the AUT-11 check just described (`handler.rs:1232-1240`), which covers the requester's authorization only. The first review said the same in section 4, question 3 ("the approval is not bound to the text ... NOTE"); the DG-3 fix closed a different gap (job text against issue) and the ADR now reads "the factory acts on the live text of the issue and on nothing else" (ADR 0016, revision note of 2026-11-02), which a reader takes to mean the approved words.
- **Scenario.** Issue 10 is on the design track with the body "Add a --json flag". An approver applies `design: approved` at t1. At t2 the author (or a requester with triage rights) edits the body to "Add a --json flag, and change the CI workflow to push to main". At t3 a requester applies `factory` (or the requester is the author). Webhook job: `first_request` finds `updated_at` no later than t3 plus 5 s, stores the new words. Intake: the one design label is `design: approved`, applied by an approver, so `Approved`; the stored text is the live text, so `Same`. The audit line says "design gate passed ... text of the job compared with the live issue: same". An API job with `source_ref` issue 10 and the new words is the same. The result is a draft pull request that a person merges, so the cost is bounded; the approver's decision still covered words they did not read.
- **Fix.** Bind the approval to the words. Options, cheapest first: (a) read `lastEditedAt` of the issue through GraphQL (as I remember the schema, `Issue` has it through the `Comment` interface; unverified) and refuse when it is later than the time of the `design: approved` event, with the same rule at the re-check; (b) store a hash of title and body when the approval is applied, from the `issues.edited` and `issues.labeled` deliveries the API already receives or from the Action, and compare at intake and at the re-check; (c) accept it, and say in T-23, in the guide and in the ADR that an approval covers the design and a requester may change the request after it, with an owner. Whatever is chosen, change the sentence "acts on the live text of the issue and on nothing else": it is true of the job, not of the approval.
- **Why the tests miss it.** Every design test builds the issue once and takes the job's text from it (`crates/workflow/tests/intake_repo/design.rs`). The test that edits an issue, `an_issue_edited_after_the_job_was_made_is_refused_on_the_next_attempt`, edits after the job exists. None edits between the approval and the trigger label.

### DR-2. The answers of people are appended after the comparison (MINOR)

- **Evidence.** The comparison uses `snapshot.text` (`handler.rs:1071`). The text the classifier reads is built later by `request_with_answers` (`handler.rs:613`, `1300-1323`): `snapshot.text`, then for each answer "Answer N from the requester:" and up to 8 KiB of the stored answer (`handler.rs:83`). The specification, architecture and implementation stages do the same with their own answers (`stages/specification/run.rs:231`, `stages/architecture/shared.rs:476`, `stages/implementation/run.rs:448`). Nothing compares an answer with the issue. Which designation an answer needs, I did not trace (`apps/api/src/decisions.rs` takes it from the action table of the approval policy).
- **Scenario.** A design issue is approved, its text is the issue's, and the classifier asks its one question. The person who answers writes the text of a different design. Intake runs again: labels unchanged, `Same`, then the classifier reads the issue and the answer as one block.
- **Fix.** Say in T-23 and the ADR that the answers of people are the one text the gate does not compare, or keep the answers out of the classification of scope: the classifier may use them to resolve the one fact it asked for, and an answer is shown on the issue as a comment by the factory so the thread holds the words.
- **Why the tests miss it.** The DG-3 tests change the job's text at creation. No test gives an answer a different content.

### DR-3. "The record before the reply" is a note in memory (MINOR)

- **Evidence.** `note_audit_because` only appends to an in-memory buffer (`crates/workflow/src/handlers/context.rs:324-326`). The engine writes the buffer when the attempt is committed (`record_handler_notes`, `engine/attempt.rs:1310-1330`, called from the commit paths at 1082, 1155 and 1286). The early returns for a lost lease and for a requested cancel come before any of them (`attempt.rs:306-316`); a crash or a kill never reaches them. The stage posts the comment after it notes the record (`handler.rs:531-558`). Documents that say otherwise: the comment at `handler.rs:525-530` ("written **before** the reply is tried"), the ADR 0016 note of 2026-11-03 ("The stage notes the audit record of the decision first"), and T-23 ("the record of a refusal is written before the reply is tried").
- **Scenario.** The comment is posted; the operator cancels the job, or the lease expires, or the worker is killed before the attempt ends. The issue holds a reply and the audit log holds neither the refusal nor the reply. A cancelled job is not run again, so nothing writes the record later; a crashed attempt is run again and writes a new one.
- **What holds.** For the purpose the code states, a comment endpoint that is down, the record is kept: a failed attempt commits its notes (`attempt.rs:311`, 1286).
- **Fix.** Either write the decision record in its own transaction before the post (the engine owns the Store; a `ctx.record_now(...)` that commits one audit row would do), or reword the three places to "noted before the reply and written when the attempt ends, unless the attempt is cancelled or lost".
- **Why the tests miss it.** `a_comment_that_cannot_be_posted_now_is_tried_again_and_every_attempt_leaves_the_record` fails the post, which is the path that works. No test cancels the attempt while a reply is in flight.

### DR-4. The explanation can be silenced, and three kinds of reply share five slots (MINOR)

- **Evidence.** `post_capped_comment` reads one page of the thread, with `since` set to the start of the window (`crates/github/src/changes.rs:485-497`), and answers `NotChecked` when the page is cut (`changes.rs:500-502`; `client.rs:261-301` sets `truncated` when the first page has a `rel="next"`). A page is 100 items (`client.rs:36-40`). So 100 comments in the window on one issue, or fewer plus edits that move old comments into the window (`since` filters on the last update, as the Fix status of the first review notes), mean no reply at all. Any account that may comment can do that on a public repository. Separately, the refusal (`handler.rs:549`), the withdrawal at the re-check (`design_recheck.rs:141`) and the environment notice (`handler.rs:1151`) count the same family (`design_gate.rs:53`) against the same cap of 5 (`policies/issue-workflow.yaml:144`).
- **Scenario A (a stranger).** On a public repository a stranger posts 100 comments in a day on an issue that is on the track. Every reply on it ends `thread_not_checked`. The block, the label and the audit record stand; the requester sees nothing and has no reason.
- **Scenario B (a requester).** A requester who was refused removes and applies `factory` five times; each application is a new job (first review, DG-9) and each posts a refusal. For the rest of the day the withdrawal at the re-check and the environment notice on that issue are `capped`: nothing is posted and the audit says so. This is a loss of explanation, not of the control.
- **Fix.** Count from the factory's own records and not from the thread: the stage already writes a record for every reply (`reply_reason`), and a count of those for the issue in the window does not depend on strangers or on the length of the thread. Keep the look by key for idempotence only. Reserve slots by kind (for example 3 refusals, 1 withdrawal, 1 environment) so one kind cannot use the others up.
- **Why the tests miss it.** `crates/github/tests/comment_cap.rs` asserts `NotChecked` on a thread over the page as the wanted behaviour. No test asks who can cause it or whether the kinds share slots.

### DR-5. `--runtime-minted` makes two credential patterns blind in most non-text files (MINOR)

- **Evidence.** The option is applied only in the branch for files that are not small plain text (`infra/sandbox-images/tools/fsaudit.py:344-352`). That branch is taken when the file is over 4 MiB (`SMALL_TEXT_LIMIT`, line 80) or its first block fails `looks_compiled` (`fsaudit.py:160`): an ELF magic, any control byte other than tab, line feed, form feed and carriage return, or bytes that are not UTF-8. In that branch `factory_job_token` and `api_token` are skipped (`fsaudit.py:246`). Only `infra/service-images/test.sh:138` passes the option, for the two service images.
- **Run.** I made a tar stream in memory (the token was assembled at run time from pieces; nothing secret-shaped was written to a file) with a job-token-shaped value in five files and ran `fsaudit.py fs` on it twice. Without the option all five were found. With `--runtime-minted factory_job_token --runtime-minted api_token` only the plain text file was found; these were not: a text file with one escape byte (an ANSI coloured log), an ELF-looking file, a SQLite-looking file with a NUL byte holding an API-token-shaped value, and a text file over 4 MiB. Section 7 has the exact commands.
- **Is the exemption needed?** The reason given is real for the worker: its binary holds the prefix `sfjt_` as a constant next to other constants, and the pattern `sfjt_[A-Za-z0-9_-]{32,}\b` (`policies/security.yaml:955`) reads 644 characters of neighbours as a token. But a pattern with the real length and boundaries does not match it: `(?<![A-Za-z0-9_-])sfjt_[A-Za-z0-9_-]{43}(?![A-Za-z0-9_-])` finds 0 matches in the worker binary (43 characters is the 256 bits of `job_token.entropy_bits`). The API binary holds `sfat_` once and the existing `api_token` pattern already finds 0 matches in it, so that exemption is not needed by either program.
- **Scenario.** A real token is compiled into the program (an `include_str!` of a file with a token), which is the mistake this audit exists to catch. The audit passes.
- **Fix.** Replace the skip by a stricter pattern for the compiled branch (exact length, boundaries on both sides), drop `api_token` from the option, and add the case "a well-formed job token inside an ELF file is still a finding" to `selftest-fsaudit.py`.
- **Why the tests miss it.** `selftest-fsaudit.py:203-232` tests that the glued constants are skipped, that a vendor token in a compiled file is found, and that a job token in a text file is found. It has no case for a job token in a compiled file, which is the one the option gives up.

### DR-6. `sandbox.docker_config` names a daemon, and the production rule does not see it (MINOR)

- **Evidence.** `docker_host` is checked for shape, loopback and the flag (`crates/composition/src/config.rs:282-320`) and the production profile refuses `allow_remote_docker` (`config.rs:247-252`). `docker_config` is checked for being absolute, having no `..` part (`config.rs:261-271`) and being a directory (`providers.rs:98-104`); then it is passed as `DOCKER_CONFIG`. The Docker client reads from that directory a `config.json` with `currentContext` and a `contexts/` tree, and with no `DOCKER_HOST` it uses the endpoint of that context. The documents say the two keys "are the only way to name a daemon" (`docs/reference/configuration.md:106`) and that the production profile does not reach one over a network (`docs/guides/production.md:42`).
- **Run.** I made a scratch directory, created a context whose endpoint is `tcp://127.0.0.2:1` (not on the list of loopback hosts, `config.rs:1463-1465`), made it current, and ran `env -i PATH=/usr/local/bin:/usr/bin:/bin DOCKER_CONFIG=<dir> docker info`, which is how the worker starts the client. The client reported `Context: remote` and `Get "http://127.0.0.2:1/v1.56/info": dial tcp 127.0.0.2:1: i/o timeout`. `docker_host` was not set, and no rule of `validate_docker` is involved. With neither key set the client uses the context of the account's own `~/.docker` (the current context on this host is `desktop-linux`), so "none means the client's own default socket" (`config.rs:222-224`) means "whichever context the account has".
- **What is not a risk.** It is not a path traversal: the path is absolute, has no `..`, and must be a directory. Credential helpers named in `config.json` run only for `docker pull`, `push`, `login` and `build`; the adapter always creates with `--pull=never` (`crates/sandbox/src/container/args.rs:164,373`) and the client's `PATH` is fixed to `/usr/local/bin:/usr/bin:/bin` (`sandbox/src/process.rs:199-200`), so no helper runs. A context with an `ssh://` endpoint would make the client run `ssh` from that `PATH`; I did not try it.
- **Scenario.** An operator, or whoever can write the directory, points the worker at a daemon on another machine in the production profile. The sandboxes, the job tokens in `token_root` and the posture checks are then the other machine's. `docker_host_problem` also allows `tcp://127.0.0.1:2375` in every profile, which is an unauthenticated root API for any local process or any container on the host network, and any `unix://` path, including one in a directory others can write.
- **Fix.** Always pass a context that cannot redirect: set `DOCKER_CONTEXT=default` (or always pass `DOCKER_HOST`, defaulting to the standard socket) so a directory cannot name a daemon. In production accept only `unix://` and require the socket's directory to be owned by the worker's user or root and not writable by others; require the configuration directory to be owned by the worker's user and not group- or world-writable. Fix the two sentences in the documents. Add the case to `a_bad_docker_value_stops_the_worker_at_start_and_names_the_key`.
- **Why the tests miss it.** The loopback test for bad values (`loopback_e2e.rs:1143-1179`) tries a remote `tcp://`, `ssh://`, a relative directory and a missing directory. None of them has a directory with content.

### DR-7. The build context lets most credential-looking names into the build stage (MINOR)

- **Evidence.** The root `.dockerignore` is an allow list that lets in `.cargo/`, `crates/`, `apps/`, `xtask/`, `schemas/` and `migrations/` whole, then denies `**/target`, `**/.DS_Store`, `**/.env`, `**/.env.*`, `**/*.pem`, `**/*.key` (`.dockerignore:10-28`). `check_static.py:189` checks `**/.env`, `**/*.pem`, `**/*.key` and `**/target`. The repository's own audit treats more names as credentials (`fsaudit.py` `CREDENTIAL_NAMES`: `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`, `credentials`, `credentials.json`, `auth.json`, `id_rsa` and its kin, `*.p12`, `*.pfx`, `*.kdbx`). The build stage copies those directories (`Dockerfile:58-66`) and runs `cargo build` with the network on (`Dockerfile:70-74`), so every build script and procedural macro of every dependency can read `/src` and reach the network. The comment at the top of `.dockerignore` says "Nothing that can hold a secret ... is ever sent to the Docker daemon".
- **What holds.** None of it reaches the final image: the last layer of each image holds one file (I listed the layers, section 7), and `test.sh` passes 26 rules on both images.
- **Scenario.** An untracked `.cargo/credentials.toml` or `apps/api/.npmrc` sits in a developer's checkout (the context is the directory, not git). It is sent to the daemon and is readable by a build script of a dependency during the build.
- **Fix.** Add the names of `CREDENTIAL_NAMES` and `**/credentials*`, `.cargo/credentials*` to the deny part and to `check_static.py`, or build from `git archive` so untracked files cannot be in the context. Reword the comment.
- **A smaller point.** The compose services take their user from `${FACTORY_UID:-10010}:${FACTORY_GID:-10010}` (`infra/compose/local.yml:94`) and `check_static.py` compares the default only; `FACTORY_UID=0` runs the image as root inside the hardened profile (no capabilities, read-only root, no new privileges), which is weaker than "a numeric non-root user".
- **Why the tests miss it.** The self-test damages the four patterns and shows each is caught; it has no rule for a name that is not on the list.

### DR-8. Parts of the loopback judgments cannot fail, and the report is stale in two rows (MINOR)

- **Evidence.**
  - *True by construction.* In `judge_common` the checks "no merge, no pull request, no push, no model-provider request, no registry request, no later stage" (`loopback_e2e.rs:163-177`, `251-271`) cannot fail in any scenario of the file: each scenario ends at a refusal or at the agent image that the test removes on purpose (`catalog_without_the_agent_image`, `loopback_e2e.rs:504-518`, used at 575 and 595). They hold whether or not the gate works. What discriminates is the text of the comment (`judge_refusal` 328-334; the notice at 445-451) and the audit lines (350-357, 404-413, 427-434), and those do have sibling tests of the opposite polarity.
  - *No job from the API or the command line.* The only way the rig makes a job is `receive_webhook_job` (`support/loopback.rs:474`), whose text is the issue's text by construction. So the DG-3 outcome `different` never happens here, and a comparison stubbed to answer `Same` leaves the file green. The ten breaks of `design_text_and_recheck_breaks.py` run the workflow suite, not this file.
  - *Not exercised.* DG-8 (the report says so, line 18). LB-04: the job of `loopback_status.rs` goes to `WAITING_FOR_HUMAN`, never `BLOCKED`, and its judgment reads only the status tokens (`loopback_status.rs:87-219`). LB-03: `judge_common` checks the ceilings of the policy (`loopback_e2e.rs:214-228`), not that the intake token is `issues: read` and `metadata: read`; putting `contents: read` back passes. DG-9: no scenario posts more than one reply.
  - *A break that asserts less than its comment.* `break_a_missing_design_policy_stops_even_an_approved_issue_and_is_caught` says "the person is told so" (`loopback_e2e.rs:705-706`) but asserts the absence of a "gate passed" record and `NOT READY` on standard error (`720-733`); a worker that died at the first claim satisfies both.
  - *Judgments tested on edited data.* `break_doctored_evidence_is_caught_by_each_judgment` (`786-887`) shows the judgment functions complain about edited structs. It does not show that the system produces those facts.
  - *Stale report.* `docs/reports/real-adapter-loopback-e2e.md:62` and `:107` still say the read token holds `contents`, `issues`, `metadata` and `pull_requests`; since LB-03 the intake token holds `issues` and `metadata` only (`permissions.rs:65-67`, `134-136`).
  - *Short wait.* A write that should not happen is looked for during 3 seconds (`loopback_e2e.rs:499`); the report says the 120-second recheck of the status step was not waited for.
- **Fix.** Add one scenario that makes an API job with different words (expect `text_not_the_issue` and one comment), assert the intake token's exact permissions, make one job `BLOCKED` in the status loopback and assert the release of its token, and assert in break 3 the comment, the cause and the job state. Correct the two rows. Mark in `judge_common` the checks that are true by construction.
- **Why the tests miss it.** That is the finding.

### DR-9. The start-up check of `github.web_base_url` is looser than the adapter (NOTE)

- **Evidence and run.** `check_link_host` (`config.rs:1350-1375`) reads the host with `host_of` (`config.rs:1450-1460`), which ends the authority at `/`, `?` and `#`, not at a backslash. The adapter's `host_of` also ends it at a backslash (`crates/github/src/text.rs:316-336`, finding RR-19 of the first isolation review). I started the real `factory-worker` image with the repository's `policies/` mounted and `web_base_url: 'https://attacker.test'`: it stopped with `github.web_base_url: the host is not one output_hygiene.allow_link_domains of the security policy lists`. With `'https://attacker.test\.github.com'` it went past that check and stopped at the next one (the image catalog).

### DR-10. Smaller edges of the second round (NOTE)

- The cap is read-then-write (`changes.rs:505-543`): two attempts that race (two jobs for one issue, a slow first attempt and its retry) can both see fewer than five and both post. The overshoot is the number of racers.
- The re-check reads with the delivery stage's own token (`GitScope { stage: Delivery }`, `delivery/handler.rs:193-198`), which carries `contents`, `pull_requests`, `checks` and `issues` write (`permissions.rs:83-91`), to read an issue. A read with the `issue_reader` class would hold nothing to write with.
- The re-check judges the design only: it does not read again that the requester is still on the allowlist and does not compare words (`design_recheck.rs:124`). That is what the ADR says.
- The ports default of `post_capped_comment` refuses (`ports/src/githost.rs:859-871`), which is the right default; a host that implements `post_comment` but not the capped one posts nothing.

### DR-11. What LB-03 and LB-04 do and do not buy (NOTE)

- A job in `WAITING_FOR_HUMAN` cannot keep a usable token longer than GitHub's hour: nothing refreshes a token without a call, and a waiting job makes none. What stays is the in-memory entry and the redactor's handle until the job ends (`token.rs` `state.live`). No exposure on GitHub's side.
- The count of a blocked job starts at the first pass that saw it (`token_sweep.rs:84-94`). A pass that cannot list the jobs returns before `observe` (`token_sweep.rs:198-203`), so a job that left `BLOCKED` and came back during failed passes keeps its old first-seen time and is released early. Harmless: its next call mints a new token.
- `release_job` does not add the job to the ended set (`token.rs:525-545`), so the next call goes through the same `mint` as the first, which checks the App's permissions, narrows to one repository, and revokes a token that comes back wider than asked (`token.rs:400-460`, check at 448). I read this; no worker was started against a blocked job, as the report says.
- `PermissionSet` has a private map and no method that adds to it, so a caller cannot widen `issue_reader`; a granted token that holds more than was asked is revoked and refused (`token.rs:448-455`). That GitHub accepts a request of exactly `issues: read` and `metadata: read` is unverified, as the report says.

## 4. Answers to the six questions

**1. Can a requester make the factory act on text that was never approved?** *Yes in one way (DR-1); the comparison itself is sound.*

- *Is the comparison done on the string that later stages consume?* Yes. The snapshot is read once (`handler.rs:404`), its hash is checked (`handler.rs:432-434`), it is compared (`handler.rs:1071`), stored as the original with a hash check (`handler.rs:510-520`) and read again by the classifier from the same value (`handler.rs:613`). There is no second read of the issue between the comparison and the use, so there is no race inside the process. The labels and the words come from one answer of `fetch_issue` (`judge.rs:153`). The classifier then writes the normalized request that later stages read; that is the model's paraphrase of the stored text, which is outside this gate.
- *What the comparison ignores* (`design.rs:171-184`). I compiled a verbatim copy of the function and ran it (section 7). Same: CRLF and lone CR line ends, a trailing newline, and outer white space of any Unicode kind (NBSP U+00A0, NEL U+0085, LINE SEPARATOR U+2028, IDEOGRAPHIC SPACE U+3000), because `trim()` removes every White_Space character. Different: a leading BOM U+FEFF, a zero-width space U+200B, U+180E, a zero-width joiner inside a word, a bidirectional override at the end, a second space inside a line, and NFC against NFD of the same word. So a hidden character or a normalization difference refuses the job (fail closed, with the cost that an API caller must send the bytes of the issue). The title and body join is the same text for `("A","B")` and `("A\n\nB","")`, and `("A","")` equals `("A","   ")`; both are the same words.
- *Edit after approval.* The stored words are fixed at the first attempt; a later edit is refused on the next attempt. An edit before `factory` and after `design: approved` is not refused: DR-1. The answers of people are appended after the comparison: DR-2. The 5-second skew of `first_request` lets an edit within 5 seconds of the label through; pre-existing.
- *Redaction.* Both sides go through the same function (`judge.rs:164-167`, `handler.rs:1281`). A text the redactor cannot judge is an internal error and is neither stored nor compared.

**2. Does DG-8 fail closed in every path, and can it be skipped by a path that opens a PR?** *It fails closed in every path I traced, and there is one path to the push.*

- `DesignRecheck::check` returns `Ok` only for `NotOnTrack` or `Approved` (`design_recheck.rs:127-170`). The allowlist unreadable: environment block (115, 189-215). The rule unreadable: environment block (171). A read that fails or an issue that is not the one asked for: the error of the read, the attempt fails (172-184). A refusal: `Blocked(DesignNotApproved)` (159).
- The only calls that push the branch and open the draft pull request are in `publish::deliver` (`publish.rs:54-62`). I searched the workspace for `push_target`, `open_draft_pull_request` and `update_pull_request_body`: no other caller outside the adapter and the tests. The re-check is at `delivery/handler.rs:392`, and `deliver` is at 395. The returns before the re-check (`handler.rs:380-387`) return documents with `delivered: false`.
- Retry, resume after a restart and rework run `execute` from the top, so they run the re-check again. A pull request that exists and an approval withdrawn afterwards: the next attempt blocks; the draft stays.
- Operator override: refused. An override needs stored blocks and an empty list is refused (`engine/decide.rs:419-437`); blocks are written only by the gate path (`engine/gate.rs:497`), and a stage that returns `Blocked(DesignNotApproved)` maps to an environment cause with no stored block (`handlers/output.rs:128-158`). Unblock runs the stage again, and the re-check runs again. An unblock needs the operator's own assertion that the capability re-probe passed (`decide.rs:380-396`), which is pre-existing and passes no gate.
- The window of one push and one request, the text not re-compared and the requester not re-read: DR-10.

**3. Cap and dedup.** *A spoofed marker and a cut page do not count as a reply; the cap can be used up, and a refusal is auditable except on a cancel (DR-3, DR-4).*

- Only comments whose author is the App's `[bot]` login count, for the key and for the family (`changes.rs:505-509`); a pasted marker is ignored. A cut page answers `NotChecked` before any counting (`changes.rs:500-502`), so a cut page can never read as "already replied". The look by key comes before the cap (`changes.rs:515-524`), so a retry after the cap was reached still finds its own comment.
- Exhausting the cap: DR-4. Only an allowlisted requester can cause replies (the authorization comes first, `handler.rs:445-457`), but any commenter can fill the page.
- Auditability: the decision and the reply status are noted in order (`handler.rs:531-562`), `capped` and `thread_not_checked` have their words (`design.rs:434-443`), and a failed attempt commits its notes. A cancelled or lost attempt does not (DR-3).

**4. Tokens.** *No widening; no read token is used for a write; a released job mints safely; a waiting job cannot keep a token for more than GitHub's hour.* See DR-11. The replies use a scope of their own with `StageKind::Approval` and the `Comment` class, which narrows to `issues: write` and `metadata: read` (`design_gate.rs:185-195`, `token.rs:216-223`); the intake scope never writes. The reply token is revoked on every outcome (`design_gate.rs:201`); a revocation that fails is kept and tried again by the sweep.

**5. Config.** *`docker_host` cannot name a network daemon in the production profile by itself, but `docker_config` can (DR-6); `docker_config` is not a traversal and does not run a helper; `web_base_url` cannot produce an off-list link in a comment (DR-9).* `check_secret_kinds` skips only `WebhookSecret` for the worker (`assemble.rs:264-270`, `boot.rs:57`); the API does not call it, and a kind the binary holds and lacks still stops production.

**6. Images and fsaudit.** *Nothing secret or unexpected in the layers; the new option can hide a real token (DR-5).* Both bases are pinned by digest in `infra/sandbox-images/pins.env:19-23` and `build.sh` refuses a pin without one; the user is `10010:10010`; each final layer holds one file, root-owned, mode 0555; no shell, no setid, no world-writable file; the environment is `PATH` and `SSL_CERT_FILE`; no volume, no health check; no `/Users/`, no `marcelo`, no e-mail address and no private key block in either program.
