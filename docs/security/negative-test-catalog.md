# Negative test catalog

Status: DESIGNED. None of these tests exists yet. This catalog defines what a QA engineer should build and what each test must prove.
Date: 2026-10-27. Revised the same day to match ADR 0003, 0005, 0006 and 0009 (details in section 2.1): the agent CLI runs inside the sandbox, so tool-call assertions are made at the boundaries the factory controls; authority comes from a named allowlist; the rework cap is two rounds; every new direct dependency needs a human; skills and slash commands follow a per-stage profile. Revised again after the agent-runtime spike (`docs/spikes/agent-runtime.md`) and ADRs 0010, 0012 and 0014: the [C] parts now say what Claude Code and Codex expose (NT-INJ-07, NT-POL-08, NT-TOOL-04, NT-TOOL-05, NT-BUD-07); budget exhaustion and a failed output go to a person, so NT-TOOL-09 expects that the stage does not advance; the factory never marks a pull request ready (NT-MRG-08); NT-AUTHZ-05 uses the state of ADR 0010; NT-TEN-01 is required in Slice 1 (P0); and NT-TOOL-03 has its number from `tools.misuse_threshold`.
Source requirements: master prompt section 16 (tests for unauthorized actions, prompt injection in issues and repository documents, malicious tool requests, merge races, policy bypass, failing checks, token exhaustion), the "Required tangible implementation evidence" paragraph (prompt injection resistance, sandbox boundary behavior, test-file protection, human review gates, inability to merge on failing evidence), and the threats in `docs/security/threat-model.md`. Crash recovery tests are out of scope here.
Policy keys referenced below are in `policies/security.yaml` and `policies/approval.yaml`.

## 1. Test principles

1. **Containment, not persuasion.** A deterministic test cannot show that a real model resists an injected instruction. The gating tests assume the model is fully controlled by the attacker and use a scripted adversary (FX-ADV, FX-EXEC or FX-ADV-P, section 2.1) that does exactly what the attacker's text says. The assertion is that the sandbox, the broker, the policy and the gates stop the effect. Susceptibility of real models is measured separately by non-gating evaluations in `evals` and is reported as a rate with confidence intervals. It never replaces a containment test.
2. **Every test must be able to fail.** For each test there is a "control off" switch in the test harness (disable the one control under test). The test must fail when the switch is on. A test that passes with its control removed is not accepted. This follows the security standard that mitigation tests fail when the control is removed.
3. **Assert on durable facts**, not on log text: database rows, audit events, the fake GitHub request log, filesystem state, container state from `docker inspect`, process spawn records, captured prompts.
4. **Missing environment is not a pass.** Tests that need Docker, PostgreSQL, NATS, MinIO or an installed agent CLI report BLOCKED when the dependency is absent. The CI job for this suite must provide them (the project environment has Docker 29.9.2, PostgreSQL client 18.6, nats-server 2.15.1, `claude` 2.1.311, `codex` 0.163.0).
5. **No real network and no real credentials.** GitHub is FX-GH. Model providers are fake. Secrets are generated fakes with real formats.
6. **One test, one control.** Combined scenarios (SEC-01) exist as end-to-end checks on top of the focused tests.

Priority: P0 is required before Slice 1 (the minimal end-to-end MVP) is accepted. P1 is required before Slice 2 and 3 are accepted or before the first external user. P2 is required before more than one tenant is onboarded or before production operations (Slice 4).

Levels: unit means no I/O beyond fixtures. Integration means real PostgreSQL, NATS, Docker or filesystem with fakes for GitHub and model providers. E2E means the full pipeline on a fixture repository through the API.

Crate names follow the master prompt's workspace suggestion (`agents`, `runtime`, `sandbox`, `github`, `policy`, `quality`, `workflow`, `events`, `storage`, `observability`, `repository_intel`, `spec_adapter`, `planner`, `evals`, and the apps `api`, `scheduler`, `worker`, `dashboard`). They are proposals; the architect's ADRs prevail.

### 2.1 Where the attacker runs, and what each assertion is checked against

ADR 0005 and ADR 0009 put the agent CLI **inside** the sandbox, behind the broker. Its own tool calls (shell, file read, file write) happen inside the CLI. The factory does not see or mediate them one by one. A test that says "the policy engine denies the call and the grant table does not change" can therefore only be checked for commands the factory itself runs. For the in-sandbox agent the checks move to the boundaries the factory controls: the sandbox posture, the egress sidecar and broker logs, the host-computed diff, the filesystem audit walk and the audit log. Attack inputs are not weakened. The same inputs are run; the observable assertions change where the old ones assumed mediation.

Each assertion in the tables below carries one of these tags:

| Tag | Meaning | When it can run |
| --- | --- | --- |
| **[B]** | Boundary assertion. Checked against the sandbox posture, sidecar and broker logs, the host-computed diff, the audit walk or the audit log. The attacker is FX-EXEC (commands executed inside a real sandbox) or FX-ADV-P (a real CLI driven by a scripted provider). The assertion needs nothing from the CLI. | Once the sandbox and ingestion exist. |
| **[S]** | Supervisor-run commands. Applies to commands the factory starts itself (gates, `fetch_deps`, version control) through the typed argv wrapper: argv arrays, fixed environment, command classes, per-call limits. | Once the typed wrapper exists. |
| **[C]** | CLI-dependent. Needs something only the installed CLI can show: its event stream, permission-denial reports, skill listing or an accepted broker base URL. | The spike (`s0-agent-runtime-spike`) has proved what Claude Code 2.1.311 and Codex CLI 0.163.0 expose, so these parts run now, against a fake provider. Each test names its observable. When the CLI is not installed the test reports BLOCKED, never PASSED. |
| **[T]** | Host tool bridge only. Applies in full if a human chooses `host_tool_bridge` (off in Slice 1). | Otherwise reported NOT_APPLICABLE with that reason, never PASSED. |

Rule for acceptance. The [B] and [S] parts are always required. A [C] part reports BLOCKED, with the reason, when the CLI it needs is not installed; otherwise it must run and pass. A [C] observable is telemetry. The pass condition of a containment test stays the effect at a boundary, because the spike showed that a permission flag is a filter and not a boundary. A [T] part reports NOT_APPLICABLE unless the host tool bridge is chosen. A BLOCKED or NOT_APPLICABLE part is stated in the report and never counts as a pass.
